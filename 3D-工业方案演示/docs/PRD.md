## 0. 可行性分析

### 0.1 结论

可以做，但有一个前提：自然语言只负责“选什么、改多少、怎么动、出什么”，不让大模型直接写 three.js 代码。

- **Agent 的输出**：一份结构化的方案（下文叫 `ScenePlan`）。
- **画面怎么来**：由确定性的三维引擎画出来。这个引擎就是现在 `demo/` 里已经跑通的代码。
- **为什么这样分工**：
  - 大模型每次现写代码，画面不稳定，尺寸也没法保证到毫米。
  - 它写的代码也没法逐条校验。
  - 这和 Loomi 的做法一致：Agent 决定调哪个工具，服务端决定能不能调、参数对不对。

真正的成本在“产品入库”，不在 Agent。

- 每个新型号或新夹具，都要一次性完成：拿到模型 → 预处理 → 写参数配置（可变尺寸、范围、标品、挂点）。
- 入库以后，自然语言才能驱动它。
- 所以能覆盖多少需求，取决于产品库里有多少型号，而不是 Agent 有多聪明。

### 0.2 自然语言能驱动到哪一层

| 层 | 用户说什么 | Agent 产出 | 由谁保证正确 | 本期 |
|---|---|---|---|---|
| 1. 选择和参数 | “背负式，20 吨，车宽改 2.6 米，配卷材支架” | `ScenePlan` 里的型号、尺寸、夹具或支架 | 产品库的范围和兼容表，服务端校验 | P0 |
| 2. 动作编排 | “从开卷机取卷，送到成品库，中间去一趟充电” | 动作序列（去工位、顶升、移载、大车、小车、起升、抓放） | 闭式时间轴，现有 `route.js` 的方法 | P0 |
| 3. 镜头和出片 | “给客户老板看，出一张俯视图和 30 秒视频” | 镜头列表、讲解脚本 | 固定渲染和录制管线 | P0 |
| 4. 自由特效 | “加一个粒子光效” | Agent 现写 three.js 代码片段 | 无法保证 | 不做 |

### 0.3 逐条需求的现状

“已验证”指现在的 `demo/` 里已经跑通并测过。

| 需求 | 实现方式 | 现状 | 缺什么 |
|---|---|---|---|
| AGV 选类型（顶升或背负） | 产品库加 `agv_type` 字段；两种类型各有自己的动作：顶升是钻到支架下面顶起，背负是停靠工位后移载 | 选型界面已有，没有类型字段；顶升动作已有，背负移载动作没有 | 现有 AGV1、Z1 各属于哪一类，需要确认 |
| 选适配吨位的车体 | 按货重乘安全系数筛选产品库，服务端校核额定载荷 | 产品库只有 2 款 | 每个吨位档至少一个真实模型和额定载荷 |
| 按现场改车体尺寸 | 分段拉伸，标品只平移不变形 | **已验证**（Z1、AGV1） | 真实的可调范围和规则（现在是临时值） |
| 选支架（管材或卷材） | 车体顶面挂点 + 支架模型 + 对应货物 | 现场工位里是固定的轨道式支架，货物是程序生成的 | 支架模型、接口尺寸、适配哪些车型 |
| 起重机选类型 | 产品库按类别（单梁、双梁桥式、门式……）筛选 | 本项目没有；D 内容工厂有程序化起重机结构 | 起重机模型，或者确认可以用程序化箱梁代替 |
| 起重机参数化尺寸 | 同样用分段拉伸：主梁沿跨度拉，门腿沿高度拉；端梁、小车、司机室是标品 | 方法可复用，没有配置 | 可变尺寸、范围，以及小车随吨位怎么换 |
| 起重机选夹具 | 吊钩挂点 + 夹具模型（吊钩、电磁吸盘、抓斗、夹钳等） | 无 | 夹具模型和适配表 |
| CAD 生成现场 | DXF 按图层和块属性建场景 | **已验证**，见 [CAD 平面图约定](cad-convention.md) | 真实厂房 STP（待提供）；起重机需要轨道梁 `S-BEAM` 带标高 |
| 毫米级动作和净距 | 闭式时间轴，扫掠净距 | **已验证**（17 项测试） | 实测速度和加速度，客户的安全间距 |
| 高真实感渲染 | HDRI、PBR、阴影、导出 4K | **已验证** | — |
| 手机拍照合成效果图 | 照片标定相机，产品渲染成透明底叠加，AI 只做光影融合 | 无 | 需开发，见 0.4 |
| 讲解短视频 | 按镜头脚本逐帧录制，配字幕；配音交给 E 视频生产线 | 无（只有单帧导出） | 需开发 |

### 0.4 手机照片怎么变成效果图

有三条路，建议用第三条。

| 路线 | 做法 | 优点 | 问题 |
|---|---|---|---|
| A. 纯 AI 生图 | 照片 + 产品参考图交给图像模型 | 快，好看 | 尺寸和比例不可信。工程师最关心“放不放得下”，这条路回答不了 |
| B. 纯三维 | 只用 CAD 建的场景 | 精确 | 没有 CAD 的客户用不了，也不是“实景” |
| **C. 三维定尺寸 + AI 融合** | 用户在照片上点 4 个地面点，并给一个已知尺寸（柱距、地砖、通道宽）→ 求出相机位置 → 引擎按真实尺寸渲染产品（透明底，带接触阴影）→ 叠到照片上 → 可选再用图像模型统一光影 | 尺寸可信，不依赖 CAD；AI 那一步可以关掉 | 标定靠用户点选；照片要拍到地面 |

- **标定误差**：标定以后，把用户给的已知尺寸反算一遍，误差显示在界面上，超过 3% 就提示重新点。
- **起重机**：同理，用户在照片上标出两条轨道梁，跨度从图上量出来或者手填。
- **AI 融合的图**：标“AI 生成”，不作为尺寸依据。

### 0.5 Loomi 能借什么，要改什么

Loomi（`D:\Loomi-Desktop`）可以直接借的是运行时和工程骨架。求职领域的代码（简历、岗位、网申）不借。

**直接借用**

- Claude Agent SDK 主 Agent：`query()`、会话恢复（`conversations.agent_session_id`）、取消。
- Skills 按 `.claude/skills/<name>/SKILL.md` 放，由 SDK 自动发现。
- MCP 业务工具：服务端校验参数，并按用户和项目做数据隔离。
- `PreToolUse` 钩子只放行已登记的工具；关掉 Shell、文件系统和第三方插件。
- Express 5 + SSE 流式对话；SQLite 持久化。
- React + `@assistant-ui/react` 对话区和工作区布局。
- 不在 SDK 上面再加自研的 Brain 或 Planner（Loomi 的架构原则，照搬）。

**需要调整**

| Loomi 现状 | 本项目调整 | 原因 |
|---|---|---|
| Candidate 知识库（简历事实 + 出处） | **产品库**（型号、类型、吨位、可变参数和范围、标品、挂点、夹具和支架兼容表，每个参数带出处）+ **项目**（客户现场：照片、CAD、工况口述、方案版本） | 领域换了。Grounding 原则不变：产品库里没有的参数，Agent 不能说 |
| 对话 + 结果卡片 | 对话 + **三维视口**（有状态的画布）+ 方案卡片 | 核心交互是边说边看。视口和对话改的是同一份 `ScenePlan` |
| 工具全在服务端同步执行 | 拆成两类：**校验类**（选型、参数、净距、路线）在服务端用 Node 跑，现有 `parse-cad.js`、`route.js`、`clearance.js` 本来就是纯 JS；**渲染类**（出图、录视频）作为异步任务，交给前端视口或服务端无头浏览器执行，SSE 推进度 | 渲染需要 GPU 和浏览器；校验必须由服务端说了算，不能信前端 |
| 每轮把用户消息交给 Agent | 每轮由服务端把当前 `ScenePlan` 摘要注入上下文（不信任前端传来的状态） | 用户拖滑块改了尺寸，Agent 下一轮要知道 |
| `user_id + candidate_id` 隔离 | `user_id + project_id` 隔离；工具 schema 里不出现 `project_id`，由会话绑定 | 同 Loomi 的所有权不变式，Agent 读不到别的客户项目 |
| 桌面端优先（Electron） | **手机网页优先**：上半屏视口，下半屏对话；Electron 只作为工程师电脑端 | 营销工程师在客户现场用手机 |
| 导出 PDF / DOCX | 导出 PNG、MP4、GLB、交互页链接，并写成平台的 `MediaAsset` | 对接 E 视频生产线和平台底座 |
| — | 新增上传素材库（CAD、照片、GLB，体积大），客户照片走 `core.redact` | 客户现场属于敏感信息（PRD约定 §6.4） |

### 0.6 需要平台底座改的地方

- **`ProductSpec.category` 没有 AGV。** 现在的枚举是 overhead_crane、gantry_crane、port_crane、hoist、jib_crane、special_crane、component、other。
  - 需要提给底座：加 `agv`。
  - 还要加 AGV 用的字段：`agv_type`（jacking / piggyback）、`body_length_mm`、`body_width_mm`、`fixture`。
  - 按 PRD约定，作品里不能私加字段。
- **`MediaAsset` 已经够用。**
  - `kind` 有 rendered_image、site_composite、interactive_page、interactive_page_recording、model_3d、video_clip。
  - `generation.tool` 有 `threejs`。
  - `site` 有 `contains_customer_info`。

### 0.8 后期扩展：超大起重机科普可视化

需求方希望后期把这条赛道也接进来：

> 内容创作 / 超大起重机科普可视化（三维、动画、AR 沉浸式宣传单）/ 品牌宣传部门。
> 把超大起重机（如 1230 吨、104 米长、51 米高）的尺寸、拆解、焊缝精度做成类比动画或交互页。
> 期望：一套“起重机有多大、焊缝有多准”的动画或交互科普页。

**先说明三点**

- 这正是 D 起重机内容工厂的主报场景（#10 和参考场景），D 的 PRD 已经按“拆解 + 尺寸类比”立项。
- 接进来以后，本项目和 D 基本就是同一个作品的两种模式。所以第 13 节“是否合并”的问题更要早定。
- 「1230t / 104m / 51m」公开资料查不到（见 `research/卫华集团调研报告.md`）。在主办方确认前，演示用有官方报道的 3800t-107m 门机。焊缝精度目前没有可公开的数据。

**架构上不用推翻，只是多一种模式**

本项目的三条分工对科普同样成立：

- Agent 产出结构化方案；
- 引擎负责几何；
- 参数必须带出处。

两种模式的差别在下表：

| | 方案模式（本 PRD 的 P0） | 科普模式（后期） |
|---|---|---|
| 用户 | 营销工程师 | 品牌宣传部门 |
| 输入 | 客户工况、CAD 或照片 | 产品官方参数和新闻稿、整机模型 |
| 核心问题 | 装进客户厂里放不放得下、怎么动 | 有多大、怎么拆装、焊缝有多准 |
| `ScenePlan` | 型号 + 尺寸 + 夹具 + 现场 + 动作 | 型号 + **故事段落**（每段一个镜头和一个动作） |
| 动作库 | 行驶、顶升、移载、大车、小车、起升 | **拆解和组装**（按部件逐个飞出或归位）、**尺寸类比**（并排放参照物：楼层、汽车、足球场、人）、**测量标注**、**焊缝特写**（局部放大 + 精度数值） |
| Skill | `agv-selection`、`crane-selection` | `scale-analogy`、`anatomy-story`（可从 D 迁过来）、`explainer-script` 共用 |
| 输出 | 效果图、讲解视频 | 交互科普页（`interactive_page`）、科普动画、交给 E 剪辑 |
| 出处要求 | 产品库或客户原话 | 官方报道或主办方提供；没有出处的数字标“待确认”，不能出现在成片里 |

**引擎要补的能力**

- **超大尺度**：100 米以上的整机。
  - 需要分级细节（LOD）。
  - 相机近远裁剪面要随尺度调整。
  - 参照物库要按真实尺寸建（标准楼层高、常见车型）。
  - 现有引擎按米为单位，166 米量级没有精度问题。
- **拆解动画**：模型要按部件拆分并命名（主梁、支腿、小车、司机室……），并写清每个部件的拆解方向和顺序。这和产品入库是同一件事，只是多几个字段。
- **焊缝特写**：需要焊缝位置和精度数据；没有数据就不做。

**AR 沉浸式宣传单**

- 11-09 会议纪要写的是暂不做 AR，这里列为更后期。
- 最省事的做法：
  - 把方案导出成 GLB；
  - 网页里用系统自带的 AR 查看（iOS Quick Look 需要 USDZ，安卓 Scene Viewer 用 GLB）；
  - 宣传单上印二维码。
- 不自己做 AR 追踪。

## 1. 一句话定位

营销工程师在客户现场用一句话说清楚需求，Agent 就选好型号、按现场改好尺寸、装好夹具，放进客户厂房跑一遍工艺动作，并出效果图和讲解短视频；每个尺寸都可追溯，每个动作都精确到毫米。

**产品形态（2026-11-10 确认）**：浏览器里的工作台。左边是 three.js 三维引擎，右边是 Agent 对话区；用自然语言驱动左边的选型、改参数、动画播放和视角。Agent 架构沿用 Loomi（见 0.5、第 6 节）。整体视觉用卫华品牌色。

**功能流程（2026-11-10 确认）**：按下面 7 步走，前 6 步是方案阶段。

| 步骤 | 做什么 | 对应需求 |
|---|---|---|
| 1 | 客户图纸变三维，自动搭建客户生产环境；标定作业流程点位 | R4、R9 |
| 2 | 产品库选型，修改参数做项目适配 | R1、R2、R3 |
| 3 | 输入流程说明 | R10 |
| 4 | 按流程生成全流程动画和分步流程动画 | R5、R11 |
| 5 | 计算整个流程的实际搬运效率，可以调节拍，模拟生产时间 | R12 |
| 6 | 自动行程可视化 | R13 |
| — | **方案阶段结束** | — |
| 7 | 用方案里选定的产品自动生成结构图纸、CAD 生产图纸和工艺图纸，下发生产 | R14（后期） |

效果图、讲解短视频（R6、R7）是方案阶段的输出物，不在这 7 步的主线上。

## 2. 背景与痛点

- **讲方案靠 CAD 图纸**：客户看不懂，获客效率低（2026-11-09 会议纪要）。
- **已在小范围用 AI 生成效果图**：
  - 纯 AI 图尺寸不可信，不敢给客户当方案。
  - 而且要懂 AI 工具的人才会做，没法推广到每个营销工程师。
- **定制尺寸是常态**：通道宽度、货物规格、厂房跨度各不相同。每次改尺寸都要找研发重新出图，周期以天计。
- **需求覆盖多种产品**：AGV（顶升或背负、不同吨位、不同支架）和起重机（不同类型、跨度、夹具）。不能每种产品做一个工具。

## 3. 用户与场景

| 用户 | 场景 | 现在怎么做 | 用了以后 |
|---|---|---|---|
| 营销工程师（主用户） | 在客户车间，客户问“装进来是什么样” | 回去找研发出图，几天后发 PDF | 当场拍照、说需求，几分钟出图，当面调尺寸 |
| 营销工程师 | 会后给客户发方案 | 手工拼 PPT | 出一条 30 秒讲解视频和一个可交互链接 |
| 售前或研发（次要） | 核对营销给出的方案 | 看描述猜 | 打开同一个项目，看参数、净距和每个参数的出处 |
| 产品库管理员（次要） | 新型号入库 | — | 按入库规范交模型和配置（P1 起有半自动工具） |

## 4. 范围

**P0（本次必须做完）**

1. 对话 + 三维视口的工作台（电脑网页左引擎右 Agent，手机网页上下排），借 Loomi 的运行时和外壳，卫华品牌色。第 1 节功能流程的第 1 到 6 步都要能用对话走通。
2. **AGV 全链路**：
   - 选类型（顶升或背负）
   - 选吨位
   - 改车体尺寸
   - 选支架（管材或卷材）
   - 放进 CAD 现场跑动作
   - 计算净距
3. **起重机最小链路**（2026-11-10 确认进 P0，替代 11-09 纪要里的“暂不做吊装”）：
   - 1 种类型（双梁桥式），跨度、起升高度可调
   - 2 种夹具（吊钩、电磁吸盘）
   - 在 CAD 现场的轨道梁上跑大车、小车、起升循环
4. **手机照片合成**：手动 4 点标定 + 透明底渲染叠加，出效果图。
5. **出片**：
   - 效果图（PNG，最大 4K）
   - 讲解短视频（固定镜头脚本逐帧录制 + 字幕，MP4）
   - 写入 `MediaAsset` 并交接给 E
6. **产品库**：AGV1、Z1-1000-BZ 两款真实模型；缺的吨位档和夹具先用程序生成的示意模型，界面标“示意”。

**P1（有时间再做）**

- AI 光影融合，结果标“AI 生成”。
- 讲解视频配音：交给 E 视频生产线，或用 `core` 的 TTS。
- 起重机加单梁、门式，夹具加抓斗、夹钳。
- 产品入库半自动工具：读模型包围盒，推荐拉伸段，人工确认。
- 多方案对比（两台车并排或前后切换）。

**后期（本次不排期，见 0.8）**

- 功能流程第 7 步：自动出结构图纸、CAD 生产图纸和工艺图纸（R14）。
- 科普模式：超大起重机的尺寸类比、拆解组装、焊缝特写，输出交互科普页和动画。
- AR 宣传单：GLB 或 USDZ + 系统自带 AR 查看 + 二维码。

**不做**

- Agent 现写 three.js 代码。
- AR、消费级 360 度展示（会议纪要已排除）。
- 真实设备的定位误差和动力学仿真。
- 报价：交给 B 报价智能体，本项目只把选型结果交接过去。
- 从照片自动识别地面（单目深度），P0 只做手动标定。

## 5. 功能需求

### scene-R1 自然语言选型

- **输入**：用户口述的工况，例如“搬 20 吨钢卷，从开卷机到成品库，通道 4 米”，可以分多轮补充。
- **处理**：
  1. Agent 加载 `agv-selection` 或 `crane-selection` Skill，提取货物、重量、形态、通道、跨度等工况。
  2. 缺关键项时只追问缺的那一项。
  3. 调 `search_products` 筛选候选，并给出选型理由。
  4. 工况作为“客户口述”存进项目，记下原话。
- **输出**：1 个推荐型号 + 至多 2 个备选，每个理由引用产品库字段或客户原话；视口里换成推荐的车型。
- **验收**：
  - 30 条测试口述（mock）里，推荐型号满足额定载荷和类型约束的不少于 90%。
  - 产品库里没有的型号，一次也不能被推荐。
  - 推荐理由里每个数字都能在产品库或客户原话里找到。

### scene-R2 参数化尺寸

- **输入**：自然语言（“车宽改 2.6 米”“再短 200”），或者用户直接拖视口里的滑块。
- **处理**：
  - `set_params` 在服务端按产品库范围校验。
  - 超出范围的拒绝执行，并返回可用范围和原因，不偷偷截断。
  - 通过的写进 `ScenePlan`，引擎重新拉伸。
  - 标品（激光导航、急停、端梁、小车等）只平移不变形。
- **输出**：更新后的模型和尺寸标注；滑块和对话两边同步。
- **验收**：
  - 模型外框尺寸和参数的误差不超过 1 mm。
  - 标品尺寸不变。
  - 超范围请求 100% 被拒绝，并说明原因。
  - 用户拖滑块后，Agent 下一轮回答引用的是新尺寸。

### scene-R3 夹具和支架

- **输入**：“配卷材支架”“换电磁吸盘”。
- **处理**：
  - `attach_fixture` 查兼容表（型号、吨位、挂点）。
  - 兼容的话，挂到挂点上，并换上对应货物（钢卷、管材捆）。
  - 不兼容的话，拒绝并列出可选项。
- **输出**：装好夹具的模型；动画里货物跟着夹具走。
- **验收**：
  - 兼容表之外的组合 100% 被拒绝。
  - 夹具和挂点对齐误差不超过 1 mm。
  - 换夹具后，净距自动按新外形重算。

### scene-R4 现场导入

- **输入**：
  - DXF 平面图，按 [CAD 平面图约定](cad-convention.md)。
  - 或手机照片。
- **处理**：
  - **DXF**：沿用现有解析；起重机需要 `S-BEAM` 轨道梁带标高（约定要补这一项）。
  - **照片**：
    1. 用户在地面上点 4 个点，并输入一段已知长度。
    2. 求出相机内外参数。
    3. 反算已知长度，显示误差。
- **输出**：三维现场，或者一张已标定的照片现场。
- **验收**：
  - 不合约定的 DXF 给出可读的错误信息（现有行为）。
  - 照片标定后，已知长度的反算误差在 3% 以内才允许出图，否则提示重新点。

### scene-R5 动作编排和净距

- **输入**：“从 RM-01 取卷送到 FG-01，中间去充电”，或者“吊起钢卷移到 3 号跨”。
- **处理**：
  - Agent 只产出动作序列，例如 `[go_to RM-01, lift, go_to FG-01, lower, go_to CHG-01]`。
  - 引擎用闭式时间轴算出轨迹。
  - AGV 走 CAD 路线；起重机按大车、小车、起升三轴运动。
  - 全程扫掠计算净距。
- **输出**：可播放、可拖动的动画；最小净距；低于阈值的位置标红，并给出建议（例如减宽多少）。
- **验收**：
  - 沿用现有测试：到站误差小于 1 mm、0.01°，全程偏离路线小于 1 mm。
  - 净距低于 500 mm（演示阈值）时 100% 报警。
  - 动作序列里有不存在的工位时，拒绝并列出可用工位。

### scene-R6 效果图

- **输入**：“出一张给老板看的效果图”，或者在视口里选好视角后点导出。
- **处理**：
  - 按镜头预设（总览、跟随、俯视、照片视角）渲染，最大 3840 px。
  - 照片现场模式：产品透明底渲染 + 接触阴影，叠到原图上。
  - P1：可选 AI 光影融合，结果单独存一份，并标“AI 生成”。
- **输出**：PNG，写成 `MediaAsset`（`rendered_image` 或 `site_composite`）。
- **验收**：
  - 4K 图在电脑端 10 秒内出。
  - 照片合成图里，产品尺寸和标定比例一致。
  - AI 融合图带水印或标签。

### scene-R7 讲解短视频

- **输入**：“出一条 30 秒讲解视频”。
- **处理**：
  1. Agent 用 `explainer-script` Skill 写分镜脚本：现场痛点 → 产品亮相 → 尺寸适配 → 工艺动作 → 参数卖点 → 结尾。
  2. 每条参数卖点带出处（`Claim`）。
  3. 引擎按时间轴逐帧录制（时间轴是闭式的，逐帧结果确定，不受机器卡顿影响），叠加字幕。
- **输出**：
  - MP4（1080p，30 fps），写成 `MediaAsset`（`interactive_page_recording`）。
  - 脚本交接给 E，由 E 配音和精剪。
- **验收**：
  - 同一份方案录两次，逐帧一致。
  - 脚本里每个数字都有 `Claim`。
  - 30 秒视频在电脑端 3 分钟内出完。

### scene-R8 方案保存和交接

- **输入**：“保存”“发给视频组”“这个方案给报价”。
- **处理**：
  - 每次修改 `ScenePlan` 都生成一个新版本。
  - 交接时调底座 `/v1/objects` 和 `/v1/handoffs`。
  - 对外的素材，如果含客户信息，先过 `core.redact`。
- **输出**：项目页上可以回到任一版本；E 或 B 的收件箱收到交接。
- **验收**：
  - 回到旧版本时，模型、现场和动画完全复原。
  - `contains_customer_info = true` 的素材，未经脱敏不能交接给 E。

### scene-R9 作业点位标定

- **输入**：
  - DXF 里已有的工位（`AGV-STAT` 图层，见 [CAD 平面图约定](cad-convention.md)）。起重机吊装点还没有图层，要在约定里补。
  - 用户在视口里点地面加点位，或者对 Agent 说“在开卷机东侧 2 米加一个上料位”。
- **处理**：
  - 点位存进 `ScenePlan.stations`：编号、名称、类型（取货、放货、充电、等待、吊装）、坐标（mm）、朝向、来源（CAD、手点、对话）。
  - 点位必须落在厂房地面内，不能压在设备或墙上；起重机吊装点必须在轨道梁覆盖范围内。
- **输出**：视口里显示点位标签；点位表可以改名、改类型、拖动微调。
- **验收**：
  - 点位坐标显示到 mm，拖动后和表里的值一致。
  - 越界点位 100% 被拒绝，并说明原因。

### scene-R10 流程说明输入

- **输入**：一段自然语言工艺流程，例如“AGV 在开卷机上料位接卷，送到 2 号跨吊装位；行车把卷吊到成品库 A 区；AGV 空车回充电位”。也可以在流程表里手填。
- **处理**：
  1. Agent 把流程拆成结构化的工序 `ProcessStep[]`：序号、执行设备、动作（取、放、行走、起升、下降、等待、充电）、起点、终点、货物、停留时间。
  2. 用到的点位和设备必须存在；缺了就追问，或者列出可选项。
  3. 工序表先给用户确认，再生成动画。
- **输出**：工序表（对话区和底部面板都能看）；确认后写进 `ScenePlan.process`。
- **验收**：
  - 引用不存在的点位或设备时 100% 被拒绝并列出可选项。
  - 工序表里的每一步都能在原话里找到依据。

### scene-R11 分步流程动画

- **输入**：“播放全流程”“只看第 3 步”“下一步”“慢放吊装”。
- **处理**：
  - 全流程动画按工序表串成一条闭式时间轴（沿用 R5）。
  - 分步动画：跳到某一步的起点，只播这一步，播完停住；画面上显示步骤号、动作说明和用时。
  - AGV 和起重机可以并行；起重机按大车、小车、起升三轴运动，货物在 AGV 和吊具之间交接。
- **输出**：时间轴上按工序分段，可点任一段；镜头自动对准当前步骤的设备。
- **验收**：
  - 分步播放的起止画面和全流程里同一时刻逐帧一致。
  - 货物交接时位置误差不超过 1 mm，不穿模、不瞬移。

### scene-R12 搬运效率和节拍

- **输入**：设备速度、加减速、取放时间（产品库给默认值，标“示意”），目标节拍或班次时长；可以说“节拍改成 90 秒”“模拟一个 8 小时班”。
- **处理**：
  - 按时间轴算每一步用时、单件循环时间、每小时搬运件数、每台设备利用率，找出瓶颈工序。
  - 节拍调整：改目标节拍后，判断现有方案能不能达到；达不到时指出瓶颈和差多少秒。
  - 生产模拟：按节拍连续投料，加速播放一个班次，统计完成件数、设备忙闲、排队等待。
- **输出**：效率面板（循环时间、件/小时、利用率、瓶颈）；班次模拟的完成曲线。
- **验收**：
  - 单件循环时间等于时间轴总长，误差不超过 0.1 秒。
  - 同样的参数，模拟两次结果完全一致。
  - 速度参数全部带出处，没有出处的标“示意”。

### scene-R13 行程可视化

- **输入**：“显示行程”“看行车的大车行程”。
- **处理**：
  - 每台设备画出运动轨迹（AGV 地面路径；起重机大车、小车、起升三轴各自的行程）。
  - 统计每台设备、每个轴的累计行程和单程最大行程，标出起升最高点和最低点。
  - 甘特图：横轴时间，纵轴设备，显示行走、取放、起升、等待、空闲。
- **输出**：视口里叠加轨迹线（按设备配色，可开关）；底部面板显示行程表和甘特图，点甘特图的块能跳到对应时刻。
- **验收**：
  - 累计行程等于时间轴上位移积分，误差不超过 1 mm。
  - 起重机各轴行程不超出跨度、轨道长度和起升高度。

### scene-R14 出图下发（后期）

来源：2026-11-10 讨论录音（约 70 秒，AI 总结）。

- **前提**：客户已经正式合作，方案定稿，项目进入生产阶段。
- **链条**：
  1. 用方案里选定的产品和改过的参数，自动生成**结构图**。
  2. 结构图自动转成三维模型。
  3. 三维模型转成能直接下发生产的 **CAD 图纸**。
  4. 同时生成**工艺图**：涂装、涂漆、表面花纹或图案、文字等表面处理工艺。
- **目标**：从客户方案到生产落地串成一条线。这是会上设想的无人化工厂形态：人不做具体操作，只在大屏前确认数字和参数。
- **本次**：只在步骤条上保留第 7 步入口（灰显“后期”），不做生成。
- **待确认**：结构图和生产图纸的格式、图框和标准（国标？卫华内部标准？）；工艺图里涂装色号、文字内容从哪里来；下发给哪个系统（PLM、ERP 还是 MES）。

## 6. Agent / Skill 设计

沿用 Loomi 的结构：1 个主 Agent + 一组 Skills + 一组 MCP 工具 + 确定性服务。

```text
营销工程师（手机 / 电脑网页）
   │  对话（SSE）                    视口操作（滑块、视角）
   ▼                                   │
主 Agent（Claude Agent SDK query）       │
   │  按需加载 Skill                    │
   │  调用 MCP 工具 ──────────────────┐ │
   ▼                                  ▼ ▼
确定性服务（Node）                    ScenePlan（SQLite，带版本）
 ├─ 产品库：型号、范围、兼容表、出处         │ SSE: scene_plan.updated
 ├─ 现场：parse-cad、照片标定               ▼
 ├─ 运动：route（闭式时间轴）         三维视口（three.js 引擎，现有 demo）
 ├─ 校验：clearance、载荷、兼容              │ 出图 / 录制任务
 └─ 素材：MediaAsset、handoff、redact ◄──────┘ （前端视口或无头浏览器执行）
```

**Skills**（放在 `.claude/skills/`，只写方法，不写具体客户数据）

| Skill | 用途 |
|---|---|
| `agv-selection` | 顶升和背负怎么判别（货物形态、取放方式、工位条件）；吨位怎么定（货重 × 安全系数）；车宽和通道的关系；管材和卷材支架怎么选 |
| `crane-selection` | 起重机类型怎么判别（厂房结构、跨度、起重量、工作级别）；夹具按物料怎么选（钢卷、钢板、散料、管材） |
| `site-reading` | 读 CAD 和照片标定时，该向用户要哪些信息；标定失败时怎么引导 |
| `explainer-script` | 讲解短视频的分镜结构、时长分配、字幕写法；参数卖点必须带出处 |

**MCP 工具**

- 所有工具都在服务端校验，并按会话绑定的 `project_id` 隔离。
- 工具 schema 里没有 `project_id` 字段。

| 工具 | 作用 | 关键校验 |
|---|---|---|
| `search_products` | 按类别、类型、吨位筛选产品库 | 只返回库里有的 |
| `get_product` | 读型号详情：可变参数和范围、标品、挂点、兼容夹具、出处 | — |
| `save_site_fact` | 存客户口述的工况（原话 + 解析值） | 值必须出自用户原话 |
| `set_product` | 把型号放进方案 | 额定载荷不小于工况货重 × 系数 |
| `set_params` | 改尺寸 | 范围、步长、联动规则 |
| `attach_fixture` | 装夹具或支架 | 兼容表 |
| `import_site` | 导入 DXF 或照片 | DXF 约定；照片大小和格式 |
| `calibrate_photo` | 照片 4 点标定 | 反算误差不超过 3% |
| `set_station` | 加、改、删作业点位（R9） | 点位在厂房地面内，不压设备；吊装点在轨道梁范围内 |
| `set_process` | 写工序表（R10） | 点位和设备存在；动作和设备类型匹配 |
| `plan_motion` | 写动作序列，生成时间轴 | 工位存在，动作和车型或夹具匹配 |
| `play_animation` | 播放全流程、跳到或只播某一步、调播放速度（R11） | 步骤号存在 |
| `set_takt` | 改目标节拍、设备速度、取放时间（R12） | 速度在产品库范围内 |
| `simulate_shift` | 模拟一个班次，返回件数、利用率、瓶颈（R12） | 班次时长上限 24 小时 |
| `show_travel` | 开关行程轨迹、甘特图，返回行程统计（R13） | — |
| `check_clearance` | 算全程最小净距 | 阈值来自项目设置 |
| `set_camera` | 设置镜头预设或镜头脚本 | — |
| `render_image` | 出效果图（异步任务） | 分辨率上限 |
| `record_video` | 按镜头脚本录视频（异步任务） | 时长上限 60 秒 |
| `publish_media_asset` | 写 `MediaAsset` 并交接 | 未脱敏的客户素材拒绝交接 |

**对话里不能做的事**（`PreToolUse` 钩子和服务端共同保证）

- 改产品库。
- 绕过范围校验。
- 执行 Shell 命令，读任意文件。
- 访问别的项目。

## 7. 数据与接口

### 7.1 产品库条目 `ProductModel`

```json
{
  "product_id": "agv-piggyback-20t",
  "category": "agv",
  "agv_type": "piggyback",
  "name": "背负式 AGV 20t",
  "capacity_t": 20,
  "model_file": "product-models/simplified/xxx.glb",
  "manifest_file": "product-models/simplified/xxx.manifest.json",
  "params": {
    "length_mm": {"min": 4000, "max": 7000, "default": 5000, "step": 10, "source": "claim_..."},
    "width_mm":  {"min": 1800, "max": 3000, "default": 2000, "step": 10, "source": "claim_..."}
  },
  "standard_parts": ["laser_nav", "estop"],
  "fixture_slots": [{"slot": "top", "accepts": ["stand_coil", "stand_pipe"]}],
  "motions": ["drive", "spin", "transfer"],
  "protrusion_mm": 75,
  "demo_data": true
}
```

- 现在的 `src/parametric/*.config.json` 和 `demo/src/catalog.js` 合并成这个结构。
- 拉伸段、标品锚点仍放在 manifest 里，不放进对话可见的字段。

### 7.2 夹具和支架 `Fixture`

```json
{
  "fixture_id": "stand_coil",
  "kind": "coil_stand",
  "compatible": {"category": ["agv"], "capacity_t": [5, 30]},
  "anchor": "top",
  "cargo": "COIL",
  "model_file": "...",
  "demo_data": true
}
```

`kind` 的取值：

- AGV 支架：`coil_stand`、`pipe_stand`。
- 起重机夹具：`hook`、`magnet`、`grab`、`clamp`。

### 7.3 方案 `ScenePlan`（本项目私有对象，带版本）

```json
{
  "id": "sp_...",
```

## 8. 页面与交互

**电脑（2026-11-10 改为主形态）**

- 左边是三维引擎视口，占大部分宽度；右边是 Agent 对话区。
- 顶部是功能流程的步骤条（1 到 6 步，第 7 步灰显“后期”），当前步骤高亮；对话和点步骤条都能切换。
- 视口底部是可收起的面板：时间轴（按工序分段）、工序表、效率、行程和甘特图。
- 方案卡片（型号、尺寸、夹具、净距、版本）放在对话区里，作为 Agent 回复的结果卡片。

**手机**

- 上半屏是三维视口，下半屏是对话。
- 视口可以全屏；对话可以收成底部抽屉。

**方案卡片**

- 每个尺寸后面都有出处标记，点开能看到来源：样本、CAD，或客户原话。
- 净距不足时卡片变红，Agent 主动给出修改建议。

**视口**

- 沿用现有的三步：选型、尺寸、现场。
- 新增照片模式：在照片上点 4 个地面点，输入已知长度，显示标定误差。

**任务进度**

- 出图和录制在对话里显示进度条。
- 完成后给缩略图，并提供“交给视频组”按钮。

**品牌和标签**

- 用底座的品牌外壳（卫华红）。色值沿用 `weihua-ai-workbench/colors_and_type.css`：卫华红 `#D7000F`、深墨 `#1F2329`、浅灰 `#F5F6F7`、点缀蓝 `#2B7DE9`、点缀黄 `#F5B800`。官方 VI 色值还没拿到，拿到后替换。
- 示意模型标“示意”，AI 融合图标“AI 生成”，演示数据标 `demo_data`。

## 9. 演示脚本（约 4 分钟）

1. **开场（20 秒）**
   - 原版：一张客户看不懂的 CAD 图。
   - 对比：营销工程师打开手机网页，新建项目“某钢厂冷轧车间（演示数据）”。
2. **说需求（40 秒）**
   - 说：“搬 20 吨钢卷，从开卷机到成品库，通道 4 米。”
   - Agent 追问一句“卷是立放还是卧放”，然后推荐背负式 20t + 卷材支架，并说明理由。
   - 视口里车换好，支架装好。
3. **改尺寸（30 秒）**
   - 说：“车宽改 3.2 米。”净距变红。
   - Agent 建议改成 2.8 米；拖滑块到 2.8，净距变绿。
   - 卡片上每个尺寸都有出处。
4. **进现场（50 秒）**
   - 导入客户 CAD（演示数据），车跑完整的取卷、送卷、充电。
   - 切换跟随视角和俯视视角，显示到站误差小于 1 mm。
5. **拍照合成（40 秒）**
   - 上传一张车间照片，点 4 个地面点，输入柱距 8 米，标定误差 1.2%。
   - 车出现在照片里，出效果图。
6. **换成起重机（30 秒）**
   - 说：“这跨再加一台双梁桥式，跨度 22.5 米，起升 12 米，配电磁吸盘。”
   - 起重机出现在轨道梁上，吊起钢板移位。
7. **出片和交接（30 秒）**
   - 说：“出一条 30 秒讲解视频，发给视频组。”
   - 显示录制进度，播放成片片段，E 的收件箱收到 `MediaAsset`。

## 10. 验收标准与评测

| 指标 | 目标 | 怎么测 |
|---|---|---|
| 选型正确率 | ≥ 90% | 30 条口述测试集（mock），人工标注期望型号或约束 |
| 越界参数被拒绝 | 100% | 自动测试：随机超范围的 `set_params` 和 `attach_fixture` |
| 尺寸精度 | 误差 ≤ 1 mm | 自动测试：模型外框对照参数 |
| 动作精度 | 到站 < 1 mm、< 0.01° | 沿用 `route.test.js` |
| 净距报警 | 100% | 自动测试：构造贴墙方案 |
| 照片标定 | 已知长度反算误差 ≤ 3% | 10 张照片人工点选 |
| 讲解脚本的出处 | 每个数字都有 `Claim` | 自动检查脚本 |
| 录制一致性 | 两次录制逐帧一致 | 帧哈希比对 |
| 速度 | 说需求到出第一张效果图 ≤ 3 分钟；30 秒视频 ≤ 3 分钟 | 演示前计时 |
| 手机可用 | iOS Safari、安卓 Chrome 能跑完第 9 节流程 | 真机走一遍（现有 demo 还没在真机上测过） |

## 13. 风险与待确认事项

**风险**

| 风险 | 影响 | 应对 |
|---|---|---|
| 产品模型不够：吨位档、背负式、支架、起重机、夹具都缺 | 选型只能在很少的型号里选 | 缺的先用程序生成的示意模型，标“示意”；列出素材清单（见下）尽早要 |
| Agent 编造参数 | 给客户错误的方案 | 参数只能来自产品库或客户原话；所有修改都过服务端校验；脚本里的数字必须带 `Claim` |
| 照片标定不准（地面不平、透视太大、遮挡） | 合成图尺寸不可信 | 显示误差，超过阈值不让出图；引导用户换角度拍 |
| 手机性能和录制 | 卡顿、录制失败 | 录制放到电脑端或服务端无头浏览器；手机只预览 |
| 客户现场照片和 CAD 属于敏感信息 | 外泄 | 走 `core.redact`；交接前检查；演示一律用 mock |
| 和 D 内容工厂重复 | 评审认为重复造轮子 | 按 0.7 分工，或者合并 |
| Loomi 的求职代码和外壳耦合较深（例如 `ChatResultCards.jsx` 有 1020 行） | 拆分比预想的慢 | 只借运行时、工具注册、钩子和对话组件，卡片重写 |
