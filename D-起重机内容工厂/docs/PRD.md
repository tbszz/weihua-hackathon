## 1. 一句话定位

给**品牌宣传部门和营销工程师**：输入一台起重机的参数，几分钟内得到一个**可逐层拆开的交互科普页**（带「X 辆车吊到 Y 层楼」式的尺寸类比）；到客户厂房拍一张照片、选一个型号，得到**「装在你厂里」的效果图和带出处的卖点文案**；再按卫华文风一键生成**公众号推文**，审核后写入草稿。素材以 `MediaAsset` 交给作品 E 剪成片，成片回传后作为推文配图。

### 2.3 痛点归纳

1. **拍不了**：166.5 m 高、107 m 跨度的门机，在港口现场很难拍出「有多大」的直观感受，内部结构更是拍不到。
2. **讲不清**：「3800 吨」对普通观众没有概念，只能靠宣传人员自己找类比，换算口径不统一。
3. **做得慢**：现场效果图「已在小范围用 AI 生成」，但要靠会用工具的人，营销工程师普遍做不了。
4. **怕出错**：参数一旦和官方报道不一致，对外宣传就是事故。

| 岗位 | 现在怎么做 | 做成后怎么做 |
|---|---|---|
| **品牌宣传专员**（参考场景提报方） | 收集新闻稿参数，找设计公司或自己用 AI 做图解；3D 动画要外包，周期长；类比要自己算 | 在工作台粘贴新闻稿或选预置型号 → 确认结构化参数 → 3 分钟内得到可拆解的交互科普页和 30 秒录屏 → 一键交给作品 E 剪片 |

## 4. 范围

### P0：两天内必须演示的完整闭环

**输入 3800t 参数 → 交互科普页（四层拆解 + 尺寸类比）→ 拍一张厂房照片 → 合成效果图 + 卖点文案 → 素材以 `MediaAsset` 交给 E → 官方推文原版对照生成 AI 推文 → 审核后写公众号草稿**

## 5. 功能需求

### studio-R1 参数输入与解析

| 项 | 内容 |
|---|---|
| 输入 | 三种任选：①粘贴新闻稿或技术描述文本；②表单手填；③从「官方参数库」选预置型号（P0 预置：3800t-107m、3600t、3000t、新中式吊钩桥式示例） |
| 处理 | `spec-parse` Skill 抽取字段 → 和官方参数库 `official-specs.json` 逐项比对 → 选拆解模板 → 生成部件树 |
| 输出 | `CraneSpec`（见第 7.2 节）+ 部件树；每个字段带 `source` 和状态（`官方一致` / `用户输入` / `待确认`） |
| 验收 | 3800t 新闻稿片段解析后，起重量、整机高度、起升高度、跨度、小车数、单小车起重量 6 个字段全部正确且标「官方一致」；输入「1230t、104m、51m」时这 3 个字段标「待确认」，**不得**自动补出处 |

### studio-R2 等距交互拆解图

| 项 | 内容 |
|---|---|
| 输入 | `CraneSpec` + 模板 ID（P0：`gantry-double-girder`） |
| 处理 | `isometric-anatomy` Skill 把规格写入模板参数，运行 Node 构建脚本，生成独立 HTML 片段（SVG，四色明暗，按深度绘制） |
| 输出 | 拆解图 HTML 片段 + 部件清单 JSON |
| 交互 | 悬停整机 → 一级拆开；点击某个部件 → 二级拆开并高亮；键盘 ←/→ 按层级前进后退；右下角读数显示当前部件名称和已知参数；`prefers-reduced-motion` 下不做动画 |
| 验收 | L0–L3 四层全部可达；拆开和合拢动画 ≤ 0.8 s；桌面 Chrome 下交互不卡顿；390 px 手机宽度可正常查看；部件比例跟随跨度、高度参数变化（跨度改成 60 m，主梁明显变短） |

**拆解层级（门式双主梁模板）**

| 层级 | 部件 | 读数里显示什么 |
|---|---|---|
| L0 整机 | 整机 | 3800 t / 跨度 107 m / 整机高 166.5 m |
| L1 结构 | 主梁（双主梁）、上端梁、支腿（刚腿 / 柔腿）、下横梁、大车运行机构、上小车、下小车、司机室 | 只显示官方公开的参数（如「上下小车各 1900 t」）；没有公开数据的部件只显示名称和一句作用说明 |
| L2 机构 | 小车内部：起升机构、小车运行机构、小车架 | 名称 + 作用 |
| L3 零部件 | 起升机构内部：电机、减速机、卷筒、滑轮组、吊钩组；运行机构里的车轮组 | 名称 + 作用；减速机、卷筒、滑轮组、吊钩组、车轮组标注「卫华蒲瑞自产品类」（[pr-drive.com](http://www.pr-drive.com/)） |

> 3800t 的具体结构（支腿形式、上端梁结构、起升机构布置）**没有公开资料**。P0 按门式起重机通用结构画示意，页面角标写「结构示意，非工程图」，并列入待确认事项，请技术中心把关。

### studio-R3 尺寸类比

| 项 | 内容 |
|---|---|
| 输入 | `CraneSpec` + 换算常数表 `analogy-constants.json` |
| 处理 | `scale-analogy` Skill 由**代码计算**（不让大模型算数），生成类比句和动画参数 |
| 输出 | 类比卡片 4 张：类比句、计算过程、常数出处、动画参数 |
| 验收 | 每张卡片下方都能展开计算过程；所有常数可追溯到官方类比原文；类比句的写法统一为官方的「X 辆车吊到 Y 层楼」 |

**换算常数（从官方类比反推，需宣传部门确认口径）**

| 常数 | 取值 | 怎么来的 |
|---|---|---|
| 每辆轿车重 | 1.5 t | 官方：3000t 门机 =「2000 辆轿车」→ 3000 ÷ 2000 = 1.5 t/辆（[5585](https://www.cranewh.com/detail/5585.html)） |
| 每辆卡车重 | 15 t | 官方：3600t 门机 =「240 辆卡车」→ 3600 ÷ 240 = 15 t/辆（[5474](https://www.cranewh.com/detail/5474.html)） |
| 每层楼高 | 3 m | 官方：3000t 起升高度 120 m =「40 层楼」→ 120 ÷ 40 = 3 m/层；3800t 整机高 166.5 m 称「50 多层」→ 166.5 ÷ 3 = 55.5，吻合 |
| 标准足球场长 | 105 m | 国际足联推荐的标准球场尺寸 105 m × 68 m（通用常识，可替换为宣传部门认可的参照物） |

**3800t 的 4 组类比（计算过程写进页面）**

| # | 类比句 | 计算过程 |
|---|---|---|
| A1 | 「相当于把 **约 2500 辆轿车**一次吊到 **43 层楼**高」 | 起重量 3800 t ÷ 1.5 t/辆 = 2533 辆，向下取整到百位写作「约 2500 辆」；起升高度 130 m ÷ 3 m/层 = 43.3 层，取「43 层」 |
| A2 | 「也可以说是 **约 250 辆卡车**吊到 43 层楼」 | 3800 ÷ 15 = 253 辆 →「约 250 辆」；楼层同 A1 |
| A3 | 「整机站起来有 **55 层楼**高」 | 整机高 166.5 m ÷ 3 m/层 = 55.5 层 → 写「55 层楼」，和官方「50 多层楼」一致 |
| A4 | 「两条腿之间能放下 **一个标准足球场**，还多出 2 米」 | 跨度 107 m − 足球场长 105 m = 2 m |
| 附 | 「上下两台小车各 1900 t，单台就相当于约 1270 辆轿车」 | 1900 ÷ 1.5 = 1266.7 →「约 1270 辆」 |

取整规则写死在代码里：车辆数 ≥ 1000 时向下取整到百位，< 1000 时向下取整到十位；楼层向下取整到个位。理由：宁可说少，不说多。

**动画方式**：类比区是一个 2D SVG 场景，与拆解图同一视觉风格。车辆图标按「1 个图标 = 100 辆」堆叠计数 → 吊钩把整堆提升 → 旁边的楼层刻度尺从 0 数到 43 层；整机剪影和楼房剪影按同一比例尺并排，足球场俯视图放在两腿之间。

### studio-R4 科普页组装与录屏

| 项 | 内容 |
|---|---|
| 输入 | 拆解图片段、类比卡片、`CraneSpec`、出处列表 |
| 处理 | 按固定版式拼成单页 HTML：标题区 → 拆解图 → 类比区 → 参数表 → 出处；运行**参数一致性校验**（studio-R8）；用无头浏览器按脚本自动导览并录屏 |
| 输出 | `science-page.html`（可离线打开）、`tour-16x9.mp4`（30 秒，1920×1080）、封面截图 PNG |
| 验收 | 从确认参数到页面生成 ≤ 60 s（不含录屏）；录屏 ≤ 90 s 完成；页面底部列出全部出处链接，可点击 |

**导览脚本（录屏用，固定）**：0–5 s 整机缓慢入场 → 5–12 s 一级拆开 → 12–18 s 点开下小车，二级、三级拆开 → 18–24 s 类比 A1 动画 → 24–28 s 整机和楼房对比 → 28–30 s 收尾参数字幕。

### studio-R5 实景合成

| 项 | 内容 |
|---|---|
| 输入 | 厂房照片 1 张（手机拍摄或上传）；型号（P0 预置：新中式吊钩桥式示例配置）；用户填写的跨度和轨面高度（选填） |
| 处理 | ①照片检查（分辨率、清晰度、是否有人脸或文字标识）→ ②人脸、标识本地打码 → ③视觉模型识别厂房结构（屋架、立柱、牛腿、轨道梁），给出建议的安装位置 → ④用户确认位置 → ⑤调用图像编辑模型（照片作底图，产品图作参考图）生成 2 张 → ⑥自动质检（起重机是否在轨道梁上、是否被墙体穿插）→ ⑦用户选 1 张 |
| 输出 | 效果图 PNG（原图分辨率，长边 ≥ 1536 px）+ 生成参数记录 |
| 验收 | 单张生成 ≤ 90 s；演示照片命中缓存时 ≤ 2 s；5 张测试照片中至少 4 张的效果图被人工评为「可以给客户看」（评分标准见第 10 节） |

**拍照要求（界面上用图示提示）**

| 要求 | 原因 |
|---|---|
| 横拍，站在厂房一端沿长度方向拍，机位约 1.5 m 高 | 起重机沿厂房纵向运行，这个角度最能看出跨度 |
| 画面里要有两侧立柱和屋架，最好能看到轨道梁或牛腿 | 模型需要找到安装位置 |
| 光线均匀，避免逆光 | 合成光照更自然 |
| 不拍人脸、客户 Logo、标语、设备铭牌 | 隐私；系统会再自动打码一次 |
| 分辨率 ≥ 1920 px 长边，不开美颜和广角畸变 | 透视准确 |

**型号选择**：3800t 是港口门机，不会装进厂房，所以实景合成环节切换到厂房里最常见的**新中式吊钩桥式起重机**。P0 预置 1 个示例配置（如 20 t、跨度 22.5 m，参数在新中式公开范围 5–1000 t、10.5–40 m 以内，界面标「示例配置」）。P1 再加门式（露天料场照片）。

### studio-R6 卖点文案

| 项 | 内容 |
|---|---|
| 输入 | 型号、`CraneSpec`、照片识别结果（如「厂房偏矮」）、官方资料检索结果 |
| 处理 | 用 `core.search` 在「卫华官方公开资料」集合里检索 → 生成 3–5 条卖点，每条是 `Claim{text, evidence, confidence}` → 参数一致性校验 |
| 输出 | 卖点列表（短句，适合放在效果图上）+ 一段 80–120 字的讲解词（给 E 配音用） |

**低矮厂房对比卖点（示例）**

- 「同等起重量下，新中式整机高度降低约 30%，矮厂房也能装得下、吊得高。」出处：[findnews/183](http://craneweihua.com/findnews/183)

## 6. Agent / Skill 设计

### 6.1 总体

单 Agent：**内容工厂助手**（`studio-agent`），运行在底座的 Agent Runtime（Claude Agent SDK）上。Agent 负责理解需求、调用 Skills、和用户确认；**所有数字计算、参数比对、照片检查都由确定性服务完成**，大模型不碰数字。

```
用户输入（文本 / 表单 / 照片）
        │
   studio-agent ──────────────────────────────┐
        │                                      │
  spec-parse ──► isometric-anatomy ──┐         │
        │                             ├─► 科普页组装 ─► 参数一致性校验 ─┐
        └────► scale-analogy ────────┘                                 │
                                                                       ├─► core.review ─► MediaAsset ─► 作品 E
  照片 ─► site-composite（含卖点文案）──────► 参数一致性校验 ─────────┘
  产品图 ─► tripo-model（后台任务）─► GLB ──────────────────────────────┘
  主题 / 原版推文 ─► article-publish ─► 参数一致性校验 ─► core.review ─► 公众号草稿
        ▲ 配图：科普页封面截图 / 效果图 / E 回传成片关键帧
```

### 6.2 六个 Skills

#### ① `spec-parse`：规格 → 结构化部件树

| 项 | 内容 |
|---|---|
| 输入 | 自由文本或表单 JSON |
| 输出 | `CraneSpec`（第 7.2 节）+ `templateId` + 部件树 `parts[]` |
| 做法 | 大模型抽取字段（结构化输出）→ 代码校验单位和范围（起重量 > 0、整机高度 > 起升高度等）→ 和 `official-specs.json` 比对，标状态 → 按「类型 + 主梁结构」选模板 |
| 失败降级 | 抽取失败或字段缺失 → 弹表单让用户补；型号不在模板库 → 用最接近的模板并加「示意」角标；**任何时候都不编造出处**，查不到的字段标「待确认」；演示兜底：直接选预置的 3800t 规格 |

#### ② `isometric-anatomy`：可逐层拆开的等距交互拆解图

| 项 | 内容 |
|---|---|
| 输入 | `CraneSpec` + `templateId` |
| 输出 | 拆解图 HTML 片段 + `parts.json`（部件名、层级、读数文字） |
| 做法 | 基于开源等距拆解图引擎（见第 11 节）的绘图库，**事先手工做好参数化模板**：模板里每个部件的尺寸都是 `CraneSpec` 字段的函数（主梁长 = f(跨度)，支腿高 = f(整机高度)…）。运行时 Agent 只填参数和文案，再执行构建脚本，几秒内出图。拆开动画用引擎自带的分组弹簧动画和逐帧深度重排 |
| 为什么不现场画 | 该引擎从零设计一个新物体需要很长的会话（它的文档写明「slow on purpose」），两天内只能把模板做精，现场只换参数 |
| 失败降级 | 构建脚本报错 → 用上一次成功构建的 3800t 静态页；参数超出模板合理范围（如跨度 > 250 m）→ 按范围上限绘制并提示；浏览器不支持 → 显示静态 SVG |

#### ③ `scale-analogy`：尺寸类比

| 项 | 内容 |
|---|---|
| 输入 | `CraneSpec` + `analogy-constants.json` |
| 输出 | `Analogy[]`：`{sentence, formula, constants:[{name, value, source}], animation:{icons, floors}}` |
| 做法 | 纯代码计算 + 句式模板；大模型只在 P1 里用来润色句子，润色后再由代码复算校验数字没变 |
| 失败降级 | 某个常数缺失 → 跳过这组类比，不用大模型估算；所有类比都不可用 → 只显示参数表 |

#### ④ `tripo-model`：实拍图 → 3D 模型 → three.js 查看

| 项 | 内容 |
|---|---|
| 输入 | 产品图（PNG/JPEG，< 20 MB）或文字描述；面数上限（默认 10000） |
| 输出 | `{taskId, status, glbPath, previewUrl}` |
| 做法 | 复用已有的 Tripo 接入：上传图片 → 图生 3D 任务 → 轮询 → 下载 GLB 到本地缓存（校验 `glTF` 文件头、大小 ≤ 150 MB）→ 页面用 `<model-viewer>` / three.js 展示 |
| 失败降级 | 超时（> 3 分钟）、额度不足、生成失败 → 用**预生成的 GLB**（演示前一天生成好，按图片哈希缓存）；没有缓存 → 只显示拆解图，「3D 查看」标签置灰并说明原因；Tripo 返回的临时链接会过期，所以成功后立即落盘 |

#### ⑤ `site-composite`：厂房照片 + 型号 → 安装效果图 + 卖点

| 项 | 内容 |
|---|---|
| 输入 | 厂房照片、型号、跨度和轨面高度（选填）、产品参考图（来自预置产品图或 GLB 渲染图） |
| 输出 | 效果图 2 张（候选）、选中 1 张、卖点 `Claim[]`、讲解词 |
| 做法 | 照片检查与打码（本地）→ 视觉模型识别安装位置 → **图像编辑模型**（底图 + 参考图编辑，P0 用 Nano Banana，经复用的接入代码调用）→ 视觉模型质检 → 卖点生成（`core.search` 取证） |
| 提示词 | 全部新写，面向工业场景。要点：保留原照片的厂房结构、相机视角和光照；把参考图里的起重机装在轨道梁上，主梁横跨两侧立柱；匹配透视和接触阴影；不添加文字、水印、人物 |
| 失败降级 | ①生成超时、接口地区限制或被内容规则拒绝 → 用演示照片的**预生成结果**（按照片哈希 + 型号缓存）；②质检不通过 → 换更严格的提示词重试 1 次，仍不行就让用户从 2 张里手选；③图像接口完全不可用 → **确定性兜底**：把产品抠图 PNG 按用户拖的 4 个角点做透视变换贴到照片上（canvas 合成），效果一般但流程不断；④卖点检索不到出处 → 只输出有出处的条目，不足 3 条也不补 |

#### ⑥ `article-publish`：主题 / 原版推文 → 公众号草稿（自作品 E 迁入）

| 项 | 内容 |
|---|---|
| 输入 | 主题或官方原版推文、`Claim[]`、配图素材（科普页截图 / 效果图 / E 回传成片关键帧） |
| 输出 | `Article`（字段见底座 7.3.6 `article.schema.json`）+ 公众号草稿 `draft_media_id` |
| 子技能 | `weihua-copy-style`（感叹号标题、短句分行、「大国重器」等用语，极限用语必须有 `Claim` 支撑）、`article-layout`（排版） |
| 做法 | `core.search`（`brand_corpus` / `publicity`）取原版文风和参数 → 大模型写稿 → studio-R8 参数一致性校验 → `baoyu-compress-image` 压缩配图 → `core.feishu` 建飞书文档 → `core.review` 人工通过 → feishu-towechat `sync --commit` 写草稿 → `draft/get` 回读 |
| 失败降级 | 标题 ≤ 32、作者 ≤ 16、摘要 ≤ 120、正文 < 20,000 字且 < 1 MiB、图 < 1 MiB 为确定性校验，不过不出稿；feishu-towechat 返回 `ip_allowlist_required` 时不重试，先给 HTML 预览，等 IP 白名单确认后再写；`ambiguous` 结果不算成功；未经复核不写草稿 |

## 7. 数据与接口

### 7.1 数据来源与样例方案

| 数据 | 来源 | 方案 |
|---|---|---|
| 官方参数库 `official-specs.json` | 调研报告里的公开报道 | 人工录入 3800t、3600t、3000t、新中式参数范围，每个字段带出处 URL；开发第一天完成 |
| 换算常数 `analogy-constants.json` | 从官方类比反推（第 5 节） | 人工录入，带推算过程 |
| 官方公开资料检索集合 | 官网新闻稿（调研报告列出的链接） | 存入 `core.search` 的 `weihua-public` 集合，供卖点取证 |
| 厂房照片 | **自己拍的或公开可商用图片** | 准备 5 张：高厂房、矮厂房、带轨道梁、无轨道梁、光线差各 1 张；不用客户现场照片 |
| 产品参考图 | 待主办方提供官方产品图；临时用公开新闻配图（仅内部演示） | 授权待确认 |
