## 1. 一句话定位

给**营销业务员、销售经理和项目经理**用的飞书机器人「小华·跟进助手」：在飞书群里 @ 一下就把长篇沟通浓缩成摘要和待办，并回填客户档案；项目节点快到期或已逾期时，按确定性规则分级，自动在群里推送风险清单并 @ 负责人；群消息和语音里提到的风险自动入库；丢单原因自动归类，一键出月度成交和丢单分析报告。**全部在飞书里完成，不需要业务员换系统。**

### 2.3 痛点归纳

1. **跟进记录靠人回忆**：一个海外商机动辄几十轮 WhatsApp 和邮件，业务员写跟进小结要翻很久，经理看不到客户真实顾虑。
2. **节点到期靠人盯**：报价截止、投标截止、客户反馈、生产、发货节点分散在表格和脑子里，逾期了才发现。
3. **风险上报门槛高**：风险在群里一句话、电话里一句话就过去了，没人整理，「仅 30% 重点项目执行中上报风险」。
4. **丢单原因没法统计**：丢单说明是自由文本，人工归类费时，月报靠手写。

## 4. 范围

### P0（两天内必须完整演示的闭环）

**群里 @机器人出摘要 → 节点到期自动推送风险清单 → 一键月报**，具体包括：

| # | 能力 | 说明 |
|---|---|---|
| P0-1 | `chat-digest` 群内 @ 触发 | 读取本群最近 N 条 / 指定时间段消息，或业务员转发的合并消息、粘贴的邮件 / WhatsApp 文本、上传的 WhatsApp 导出 `.txt`；输出摘要卡片；点「确认回填」写入客户档案和项目节点 |
| P0-2 | `deadline-watch` 定时 + 字段变化触发 | 每天 8:30 定时扫描；演示模式下每 30 秒轮询节点表「最后修改时间」；确定性规则分级；推送风险清单卡片并 @ 负责人；回写风险等级 |
| P0-3 | `risk-capture` 文字 + 语音 | 群消息里识别风险 → 确认卡片 → 写入风险登记；语音消息转写后同样处理；按提交人统计 |
| P0-4 | `loss-analysis` 单条分类 + 一键月报 | 丢单记录新增时规则 + 大模型两级分类、回填标签；@小华「出 10 月月报」或点卡片按钮 → 生成飞书文档月报（数字由代码算，文字由模型写） |
| P0-5 | 4 张多维表格 + 模拟数据 | 客户档案、项目节点、风险登记、丢单记录；种子脚本按「演示当天」相对日期生成，保证演示时一定有临期 / 逾期项 |
| P0-6 | 接收 A 的 `Opportunity` 和 B 的 `QuoteResult` | 自动建客户档案和项目节点，B 的风险项写入风险登记（演示最后 30 秒用） |
| P0-7 | 评测集 | 4 个 Skill 各自的正常 / 缺失 / 风险三类用例（按 Acemode Eval 规范），评测页能一键重跑 |

### P1（加分项，有时间再做）

- 成交要素提取（#73「成交项目成功要素提取器」）：客户来源、优势、价格区间、产品型号、客户国家、沟通周期 → 单项目成交小结，沉淀成功案例库
- 多维表格「自动化」直接回调（记录变更时发 HTTP 请求），替代轮询
- 风险经验沉淀：新项目立项时按行业 / 产品类型从历史风险登记里检索出「同类项目高频风险」（参考场景「经验沉淀后新项目立项自动生成风险清单」），用 `core.search`
- 飞书邮箱直接读取（如果租户用飞书邮箱）
- 每周给业务员推「我的待办与临期节点」私聊卡片
- 卫华 AI 工作台里的 `follow` 看板页（P0 只做运行日志 + 评测页）
- 风险条目自动去重合并（同一项目同一类风险 72 小时内合并）

### 不做（明确写出来）

| 不做 | 原因 |
|---|---|
| 直连 WhatsApp Business API、读个人邮箱 | 涉及账号授权和隐私，两天做不完；改为「转发 / 粘贴 / 上传导出文件」 |
| 机器人直接给客户发消息 | 对外发送属于 H3 人工专属动作（见第 6.4 节） |
| 自动调整生产计划 | 参考场景原话「仅输出风险提醒，最终决策人工完成」 |
| 接入 SAP / OA / CRM 实时数据 | 无内部接口权限；节点数据用多维表格承载，P1 讨论接口 |
| 全量抓取所有群 | 只在机器人被拉入、且群管理员同意的项目群里工作 |
| 自建 CRM 或客户管理系统 | 与上一届「外贸客户信息管理系统」区分；我们只做飞书里的跟进层 |

## 5. 功能需求

> 编号 `follow-R*`。「卡片」均指飞书交互卡片，通过 `core.feishu` 发送；ASCII 样式见第 8 节。

### follow-R1 群内 @ 生成沟通摘要（主报 #74）

| 项 | 内容 |
|---|---|
| 输入 | ① 群里 @小华 + 指令（「总结一下」「总结今天」「总结 @张三 和客户的沟通」）；② 私聊转发的合并消息；③ 粘贴的邮件 / WhatsApp 文本；④ 上传的 WhatsApp 导出 `.txt` 或 `.eml` |
| 处理 | 取消息（默认本群最近 50 条或今天内，取较少者；可指定时间段）→ `core.redact` 脱敏 → 识别对应客户和项目（按群绑定关系、消息中的客户名 / 项目号匹配客户档案）→ 生成摘要 → 每条结论带原文定位（`Claim.evidence` 指向消息 ID） |
| 输出 | 摘要卡片：本次沟通摘要（≤ 150 字）、客户诉求、客户顾虑、下次待办（负责人 + 日期）、提到的关键数字（吨位、跨度、数量、交期、价格，原样摘出）、关联客户 / 项目；按钮「确认回填」「修改」「忽略」 |
| 回填 | 点「确认回填」后：客户档案追加一条跟进记录、更新「最近跟进时间」「客户诉求」「客户顾虑」；待办里带日期的写入项目节点（类型 = 客户反馈）；回填结果在卡片上更新为「已回填 ✓」 |
| 验收 | 20 段标注好的模拟沟通中，诉求 / 顾虑 / 待办的要点召回率 ≥ 85%；**数字和日期零编造**（输出里每个数字都能在原文中找到，代码校验）；P95 响应 ≤ 30 秒；没确认就不回填 |

### follow-R2 节点临期 / 逾期扫描与风险清单（#75）

| 项 | 内容 |
|---|---|
| 输入 | 项目节点表全部「未完成」节点 |
| 触发 | ① 定时：每天 8:30（工作日），推送到各项目群 + 管理群；② 字段变化：节点表「计划日期 / 实际完成日期 / 预计到货日期 / 状态」被修改（P0 轮询「最后修改时间」，正常 5 分钟，演示 30 秒）；③ 手动：@小华「看看风险」 |
| 处理 | **全部由确定性规则判定**（规则见 6.3 节），大模型只负责把风险清单写成一句「建议关注」的人话，不改变等级 |
| 输出 | 风险清单卡片（按红 / 橙 / 黄排序，每项 @ 负责人）；回写节点表「风险等级」「风险原因」「最近提醒时间」；红色节点自动在风险登记表建一条（来源 = 节点扫描） |
| 去重 | 同一节点同一等级 24 小时内只提醒一次；等级升高立即提醒 |
| 验收 | 30 条节点用例（覆盖各类型、边界日期、已完成、无日期）规则判定 100% 正确；字段修改后演示模式 ≤ 60 秒推送；不重复轰炸 |

### follow-R3 采购到货延迟分级（参考场景「项目全周期风险预警智能体」）

| 项 | 内容 |
|---|---|
| 输入 | 节点类型 = 采购到货 的节点：计划到货日期、预计到货日期（供应商回复）、实际到货日期 |
| 处理 | 计算延迟天数 → 按 3 天 / 3–7 天 / 超 7 天分级（6.3 节规则 D1–D4）；若同项目下游「生产」节点的计划开始日期早于「预计到货日期」，标注「可能影响生产节点 xxx」 |
| 输出 | 进入 R2 的风险清单；卡片上写明「仅提醒，是否调整生产计划由计划员决定」 |
| 验收 | 边界值（延迟 0、3、4、7、8 天，未回复预计日期）全部判定正确 |

### follow-R4 群消息风险自动抓取（#12）

| 项 | 内容 |
|---|---|
| 输入 | 机器人所在项目群的全部文字消息（需「获取群组中所有消息」权限，见 13 节）；或 @小华「记个风险：……」 |
| 处理 | 第一级：关键词 / 正则预筛（延期、推迟、缺件、没到货、变更、改图、返工、投诉、罚款、不满意、付款、卡住、来不及、delay、postpone、penalty……），未命中的消息不送模型；第二级：模型判断是否真风险，抽取「风险描述、类别、关联项目、影响节点、建议等级」 |
| 输出 | 确认卡片发给**提交人本人**（群里只出现一个小表情回应，不打断沟通）：「检测到可能的风险，是否登记？」按钮「登记」「不是风险」「改一下」；提交人确认后写入风险登记，状态 = 已确认；24 小时无人处理的进入「待确认」列表，由项目经理批量处理 |
| 身份 | 提交人取消息 sender 的飞书 user_id，通过通讯录取姓名、部门（`core.feishu` 通讯录只读） |
| 验收 | 40 条模拟群消息（含 15 条风险、25 条闲聊 / 正常进度）：精确率 ≥ 80%、召回率 ≥ 80%；不确认不入库；同一消息不重复建条目 |

### follow-R5 语音录入风险（#12）

| 项 | 内容 |
|---|---|
| 输入 | 群里或私聊发给机器人的飞书语音消息（audio 类型，opus 格式） |
| 处理 | 下载语音资源 → 转码 16k PCM → 转写（首选飞书开放平台语音识别；租户没开通或敏感模式下用本地 SenseVoice / faster-whisper，见 7.4 节）→ 转写文本走 R4 第二级 → 生成风险条目草稿 |
| 输出 | 确认卡片显示**转写原文 + 抽取的风险条目**，提交人可点「改一下」修正转写；入库时保留语音附件和转写文本 |
| 验收 | 5 段自录语音（含方言口音一段、含噪声一段）：风险要素（项目、问题、影响）抽取正确 ≥ 4 段；单段 ≤ 60 秒的语音端到端 ≤ 20 秒 |

### follow-R6 按提交人统计上报（#12）

| 项 | 内容 |
|---|---|
| 输入 | 风险登记表 |
| 处理 | 按提交人 / 部门 / 项目 / 类别 / 等级 / 来源（群消息、语音、节点扫描、报价智能体、手动）分组计数；确定性计算 |
| 输出 | 多维表格仪表盘（提交人排行、类别分布、来源占比）；@小华「风险周报」→ 卡片 + 飞书文档 |
| 验收 | 统计结果与多维表格透视结果一致 |

### follow-R7 丢单原因两级分类（#73）

| 项 | 内容 |
|---|---|
| 输入 | 丢单记录表新增记录或「丢单说明」字段被修改；或上传的当月项目 Excel |
| 处理 | 第一级规则（结构化字段 + 关键词，6.5 节）→ 第二级大模型（带分类定义和少样本）→ 合并决策；低置信或两级冲突 → `core.review` 待人工复核 |

- **为什么单 Agent**：4 个 Skill 共用同一套飞书上下文（群、客户、项目），彼此不需要协商；主 Agent 只做「理解指令 → 选 Skill → 调工具」，大量路径（定时扫描、字段变化、统计）根本不需要模型。
- **模型使用原则**：模型只做语言理解和写作（摘要、风险识别、分类、写结论）；**等级、日期计算、统计数字一律由代码决定**。
- **敏感数据**：聊天内容含客户名、金额、电话，进模型前一律 `core.redact`；支持「只用本地模型」模式（底座提供切换），本地模式下摘要质量允许下降但流程不变。

### 6.3 节点风险分级规则（确定性，`deadline_rules`）

**定义**：`今天` = 服务器所在时区（Asia/Shanghai）的日期；`剩余天数 = 计划日期 − 今天`；`逾期天数 = 今天 − 计划日期`；只对状态 ≠「已完成」「已取消」的节点判定。P0 按自然日计算，工作日 / 节假日放 P1。

**A. 通用节点（报价截止、投标截止、客户反馈、非标确认、生产、发货）**

| 规则 | 条件 | 等级 | 风险原因模板 |
|---|---|---|---|
| A0 | 计划日期为空 | 黄 | 「节点没有计划日期」 |
| A1 | 0 ≤ 剩余天数 ≤ 临期阈值（见下表） | 黄（临期） | 「还剩 N 天」 |
| A2 | 剩余天数 = 0 且节点类型 ∈ {投标截止、报价截止} | 橙 | 「今天截止」 |
| A3 | 1 ≤ 逾期天数 ≤ 3 | 黄（逾期） | 「已逾期 N 天」 |
| A4 | 4 ≤ 逾期天数 ≤ 7 | 橙 | 「已逾期 N 天」 |
| A5 | 逾期天数 > 7 | 红 | 「已逾期 N 天」 |
| A6 | 节点类型 = 投标截止 且 逾期天数 ≥ 1 | 红 | 「投标截止已过，未标记完成」（不可挽回，直接红） |

| 节点类型 | 临期阈值（剩余天数 ≤） |
|---|---|
| 投标截止 | 3 |
| 报价截止 | 2 |
| 客户反馈 | 1 |
| 非标确认 | 1 |
| 生产 | 5 |
| 发货 | 5 |

**B. 采购到货节点**（参考场景原话「采购按到货延迟 3 天/3-7 天/超 7 天分级预警」）

`延迟天数` 取以下第一个可用值：
1. 已到货：`实际到货日期 − 计划到货日期`；
2. 未到货且供应商回复了预计日期：`max(预计到货日期, 今天) − 计划到货日期`；
3. 未到货且无预计日期：`今天 − 计划到货日期`。

| 规则 | 条件 | 等级 |
|---|---|---|
| D0 | 延迟天数 ≤ 0，且（未到货时）剩余天数 > 3 | 正常 |
| D0' | 延迟天数 ≤ 0，未到货，0 ≤ 剩余天数 ≤ 3，且无供应商预计日期 | 黄（临期，「未确认到货」） |
| D1 | 1 ≤ 延迟天数 ≤ 3 | 黄（一级） |
| D2 | 4 ≤ 延迟天数 ≤ 7 | 橙（二级） |
| D3 | 延迟天数 > 7 | 红（三级） |
| D4 | 等级 ≥ 橙，且同项目存在类型 = 生产、未完成、`计划日期 < 预计到货日期（或今天）` 的节点 | 等级不变，追加原因「可能影响生产节点：xxx（计划 MM-DD）」 |

> 「3 天 / 3–7 天」原话在 3 天处有重叠，本规则取 **≤3 天为一级、4–7 天为二级、>7 天为三级**，列为待确认事项。已到货的历史延迟只计入统计，不推送提醒。

**C. 项目级汇总**：项目风险等级 = 该项目所有节点等级与风险登记中「未关闭」条目等级的最大值。

**D. 提醒去重**：同节点同等级 24 小时内不重复；等级升高立即推送；节点改为已完成后，下一轮清单中显示「已解除」一次。

### 6.5 丢单原因分类体系（`loss-analysis`）

#### 分类定义

| 代码 | 主因 | 判定要点 | 典型说法（样例） | 和相近类的区分 |
|---|---|---|---|---|
| `PRICE` | 价格 | 客户明确因我方报价高于预期 / 对手而放弃，且未点名具体竞品拿下 | 「价格高了 8%」「客户嫌贵」「预算内只能接受 XX 万」 | 点名了竞品且竞品中标 → `COMPETITOR`；预算整体取消 → `BUDGET_CANCEL` |
| `COMPETITOR` | 竞品拿下 | 项目已被具体竞争对手拿下（不论原因） | 「被 XX 拿走了」「客户选了本地品牌」「lost to a European supplier」 | 竞品赢是结果，价格是原因时：主因 `COMPETITOR`、次因 `PRICE` |
| `BUDGET_CANCEL` | 客户预算取消 | 项目本身取消、冻结、无限期搁置，客户没有向任何人采购 | 「项目砍了」「今年不投了」「资金没批下来」 | 只是推迟、有明确重启时间 → 不算丢单，标 `PAUSED` |
| `SCHEDULE` | 工期不匹配 | 我方交期 / 安装周期满足不了客户要求 | 「要求 45 天到货，我们排产要 90 天」 | 客户自己改了工期导致不满足 → 仍是 `SCHEDULE`，次因 `REQ_CHANGE` |
| `REQ_CHANGE` | 客户需求变更 | 客户改了规格、吨位、方案、范围，导致原报价 / 方案作废且最终未成交 | 「客户改成 50t 双梁，后来走了别家」「方案改成门机不要桥机了」 | 改后我方技术做不到 → 主因 `TECH`，次因 `REQ_CHANGE` |
| `QUALIFICATION` | 资质问题 | 缺少招标要求的资质、证书、业绩、认证、注册或准入 | 「没有 CE 认证」「要求 3 个同类业绩」「不在合格供应商名录里」 | 技术参数不满足 → `TECH` |
| `TECH` | 技术不满足 | 技术方案、参数、配置无法满足（含非标项做不了） | 「防爆等级达不到」「跨度做不了」 | — |
| `COMMERCIAL` | 商务条款 | 付款方式、质保、罚则、币种、贸易条款谈不拢 | 「要求 100% 货到付款」「质保要 5 年」 | 纯价格 → `PRICE` |
| `RELATIONSHIP` | 关系 / 渠道 | 客户关系、代理渠道、决策链问题（客户内定、代理倒向他家） | 「甲方早就内定了」「代理商换了合作方」 | 已点名竞品中标 → 主因 `COMPETITOR`，次因 `RELATIONSHIP` |
| `PAUSED` | 暂停（非丢单） | 项目推迟但未取消 | 「明年二季度再说」 | 自动把记录状态改为「暂停跟进」需业务员确认 |
| `UNKNOWN` | 信息不足 | 说明太短或没有原因 | 「丢了」「没成」 | **不允许猜**；卡片提示业务员补一句 |

规则：一条记录 1 个主因 + 最多 2 个次因；主因必须能在说明原文里找到依据句。

#### 两级分类流程

```
丢单说明 + 结构化字段
   │
   ├─ 第一级：规则（loss_rules，确定性）
   │    R-a 「竞品名称」字段非空 且 「结果」=竞品中标      → COMPETITOR（置信 0.95）
   │    R-b 「我方报价/中标价」差价 ≥ 5% 且说明含 贵|价格|price → PRICE（0.9）
   │    R-c 说明含 取消|砍了|不投了|冻结|资金没批|cancel     → BUDGET_CANCEL（0.85）
   │    R-d 说明含 认证|资质|证书|业绩要求|名录|CE|ISO|准入   → QUALIFICATION（0.85）
   │    R-e 说明含 交期|工期|到货时间|来不及|lead time        → SCHEDULE（0.8）
   │    R-f 说明含 明年|再说|推迟|延后 且不含 取消            → PAUSED（0.8）
   │    R-g 说明去掉标点后 < 8 个字                           → UNKNOWN（1.0，直接结束）
   │    （多条命中 → 全部作为候选交给第二级）
   │
   ├─ 第二级：大模型（带上表定义 + 每类 2 个少样本 + 第一级候选）
   │    输出 {primary, secondary[], evidence_quote, confidence, summary}
   │
   └─ 合并：
        · 规则单一命中且置信 ≥ 0.9 → 用规则结果，模型只写小结
        · 规则与模型主因一致 → 采用，置信取较大值
        · 不一致 或 模型置信 < 0.7 → core.review 人工复核（卡片发给业务员的直属经理）
        · evidence_quote 必须是原文子串（代码校验），否则视为不一致
```

### 13.2 技术与产品风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 多维表格没有原生「字段变化」事件推送 | 字段变化触发不及时 | P0 轮询「最后修改时间」（演示 30 s），P1 用多维表格自动化回调；`record-history-list` 用于确认是哪个字段变了 |
| 被动读群消息引起隐私顾虑 | 评委 / 员工不接受 | 只在机器人被拉入且群主同意的项目群工作；确认卡片只发提交人；关键词预筛后才送模型；全程脱敏；可一键关闭 |
