## 1. 一句话定位

给**报价部报价工程师**用：把客户发来的整份技术协议丢进去，几分钟内在原文上高亮出非标点、模糊项、不满足项和可偏离项，每条都带理由和出处，关键判定由确定性规则兜底，同时列出商务风险条款；报价员每改一条判断，系统就生成一条「条款—判断—报价思路」知识条目，组长审核后入库并能导出 SOP。它是现有售前软件的**上游读协议工具**，不替代售前软件出配置和报价。

## 差异化：与现有售前软件的区别与衔接（答辩必讲，独立一节）

### 一、区别

售前软件（按公开报道）的方向是 **从卫华自己的配置出发 → 生成我方技术协议、配置和报价**。本作品的方向相反：**从客户发来的协议出发 → 读懂它，找出它和我方标配的差距**。

| 维度 | 现有售前软件（公开报道，细节待确认） | 本作品 |
|---|---|---|
| 输入 | 报价员选定的型号、参数、配置 | 客户的技术协议 / 招标技术部分（PDF、Word），几十页，写法各异 |
| 核心问题 | 「我方能出什么」 | 「客户要的哪些超出标配、哪些写得不清、哪些做不到、哪些可申报偏离、哪些条款有商务风险」 |
| 判断方式 | 内部配置逻辑（推测） | 大模型抽取 + **确定性规则引擎判定**；大模型不能把规则结果改得「更有利」 |
| 结论可追溯 | 未知 | 每条判断都是 `Claim`，必须同时指向协议原文和依据条目（标配库 / 加价标准 / 历史报价 / 知识条目），点开能看原文 |
| 经验积累 | 未知 | 报价员每次改判 → 知识条目 → 组长审核入库 → 可导出 SOP → 可申请固化为规则 |
| 输出 | 我方技术协议、配置、报价 | 高亮原文、五类清单、《协议风险提示及技术偏离表》、需求参数表、知识条目、SOP |

**三件事**（答辩用一句话讲完）：

1. **读懂客户的协议**：拆条款、分配套件类别、抽参数，在原文上按五类着色。
2. **每条判断带出处，由规则兜底**：标配判定和型号一致性由代码判定；大模型只能「提交复核线索」，不能把非标改成标配、把不满足改成满足。
3. **把经验沉淀成 SOP**：改判即沉淀，回应「新人 2—3 年才能独立」。

### 二、衔接方式（不替代，接在售前软件前后）

```text
客户技术协议 ──► 【报价智能体】──► 需求参数表（型号、参数、非标项、加价点引用）
                     │                     │
                     │                     ▼ 人工录入 / 导入（接口待确认）
                     │              【现有售前软件】生成配置、我方技术协议、报价
                     │                     │
                     │◄────────────────────┘ P1：导入售前软件生成的我方协议，
                     │                         与客户协议逐条比对，补全偏离表
                     ▼
     风险偏离表、知识条目、SOP；QuoteResult ──► 作品 C（飞书跟进）
```

- **P0**：导出「需求参数表」（Excel / JSON），字段按售前软件常见输入组织（型号、起重量、跨度、起升高度、工作级别、工况、各配套件要求）。报价员照着在售前软件里录入，省去「边读协议边录」的时间。
- **P1**：如果主办方能提供售前软件的导入格式或接口，直接生成导入文件；如果能拿到售前软件生成的我方协议样例，做「我方协议 vs 客户协议」逐条比对，自动填偏离表的「我方应答」列。
- **不做**：自己算最终价格。演示里出现的加价金额只是「加价标准条目引用 + 模拟金额」，用来说明依据，最终价格以售前软件和报价员为准。

## 3. 用户与场景

### 3.1 岗位

| 角色 | 现在怎么做 | 做成后怎么做 |
|---|---|---|
| 报价工程师（新人） | 人工逐条读几十页协议，对照纸质价格表和通知；拿不准就问老员工；本地千问只能一句一句问 | 上传协议，先看系统给的五类清单和高亮，逐条确认或改判；不懂的条款点开看依据和历史知识条目 |
| 报价工程师（资深） | 凭经验读，经验在脑子里 | 只看系统标出的非标、模糊、不满足项；改判时写一句理由，系统自动生成知识条目 |
| 报价组长 | 线下逐条审组员整理的条款和思路；晨会分享记在 Excel 里 | 在「知识审核」页一键通过 / 退回；每周导出 SOP 发给组员 |
| 前端销售（#34） | 拿到客户需求不知道哪些是坑 | 看风险偏离表和「不满足」清单，提前和客户澄清 |
| 技术负责人 | — | 审批「把知识条目固化为规则」的申请，规则改动要过回归测试 |

### 3.2 核心使用流程

```text
上传协议（或接收 A 的 TenderPackage）
 → 脱敏（core.redact）
 → ① 协议解析：切条款、分类、抽参数
 → ② 非标识别：五类候选标签 + 理由
 → ③ 依据检索：标配库 / 加价标准 / 历史报价 / 通知 / 知识条目
 → ④ 规则引擎：确定性判定，决定最终标签（大模型只能升级或提线索）
 → ⑤ 风险审核：商务风险条款 + 偏离表草稿
 → 报价员逐条确认 / 改判（core.review）
 → ⑥ 知识沉淀：改判 → 知识条目 → 组长审核 → 入库 → 导出 SOP
 → 输出 QuoteResult 给作品 C
```

## 5. 功能需求

> 通用约定：所有 AI 结论用 `core` 的 `Claim{text, evidence:[source], confidence}`；所有需要人确认的动作走 `core.review`；所有进入模型的文本先过 `core.redact`。

### quote-R1 协议上传与脱敏

| 项 | 内容 |
|---|---|
| 输入 | PDF（带文字层）/ DOCX / TXT，单份 ≤ 100 页；或 A 推送的 `TenderPackage.技术协议文件` |
| 处理 | 1. 计算文件哈希，建 `QuoteTask`；2. 提取全文和页码、字符偏移；3. 调 `core.redact(text)`，默认脱敏客户名、人名、电话、合同号、金额；**比例、天数、月数、参数数值不脱敏**（风险规则要用，例如「0.5%/天」「质保 24 个月」）；4. `mapping` 只存本地，不进模型；5. 读取全局模型模式，「只用本地模型」时所有 Agent 走本地模型，检索向量也用本地 embedding |
| 输出 | `QuoteTask{task_id, file, pages, masked_text, redact_mapping_ref, model_mode}` |
| 验收 | 3 份样例协议里埋的客户名、联系人、电话、合同金额 100% 被替换；界面右上角显示模式徽标；在本地模式下断网仍能完成全流程（演示时拔网线或关 Wi-Fi 验证） |

### quote-R2 协议解析（环节 1）

| 项 | 内容 |
|---|---|
| 输入 | `QuoteTask.masked_text`（含页码、偏移） |
| 处理 | 1. 规则切分：按编号（1. / 1.1 / （1）/ 第X条）、表格行切成条款；2. LLM 为每条打配套件类别（见 §6.4 类别表，可多选）和条款类型（技术 / 商务 / 通用）；3. LLM 按类别模板抽参数（例如油漆：底漆遍数、面漆遍数、总干膜厚、颜色、防腐等级；电机：品牌、防护等级、绝缘等级、是否变频、防爆标志）；4. 型号规格用正则解析（`QD 32/10t-28.5m A6` → 型号 QD、主钩 32 t、副钩 10 t、跨度 28.5 m、工作级别 A6）；5. 抽取结果必须带原文片段（`quote` + 偏移），抽不到原文片段的参数丢弃 |
| 输出 | `Clause[]`（Schema 见 §6.3） |
| 验收 | 3 份样例协议条款切分与答案集一致率 ≥ 95%；答案集中每个非标点所在条款都被切出且类别正确率 ≥ 90%；每个参数都能定位回原文 |

### quote-R3 非标识别（环节 2）

| 项 | 内容 |
|---|---|
| 输入 | `Clause[]` + R4 检索到的候选依据 |
| 处理 | LLM 对每条技术条款给出 **候选标签** ∈ {标配, 非标, 模糊, 不满足, 可偏离} 和一句理由；同时输出「升级线索」（例如「条款提到户外沿海，可能需要 C5 防腐」）。候选标签**不是最终结论**，送 R5 规则引擎 |
| 输出 | `CandidateJudgement{clause_id, label_llm, reason, hints[], evidence_ids[]}` |
| 验收 | 候选标签和最终标签分开存储，界面能看到两者；LLM 失败或超时时该条直接按「模糊 · 待人工」处理 |

### quote-R4 依据检索（环节 3）

| 项 | 内容 |
|---|---|
| 输入 | 条款文本 + 类别 + 抽取参数 |
| 处理 | 调 `core.search(query, collection, filters)`，按顺序查 5 个集合：`quote_std`（标配库）、`quote_surcharge`（加价标准，过滤 `status=生效`，同一条目多个版本只取最新生效日期）、`quote_kb`（已审核知识条目）、`quote_history`（历史报价台账，脱敏模拟）、`quote_notice`（内部通知）。数值类参数（膜厚、防护等级、直径）用 PPTSight 的数值事实检索精确匹配，不只靠向量相似 |
| 输出 | 每条条款的 `basis[]: [{collection, entry_id, text, source:{doc, page, locator}, version, score}]` |
| 验收 | 答案集中每个非标点的「期望依据条目」出现在 top-3 的比例 ≥ 90%；加价标准有 v1/v2 两个版本时，100% 引用最新生效版本（对应 #42「随时调取最新版本」） |

### quote-R5 确定性规则引擎（环节 4，参考医晓）

| 项 | 内容 |
|---|---|
| 输入 | `Clause.params`（结构化参数）、型号规格、`basis[]`、`CandidateJudgement` |
| 处理 | 纯代码，不调模型。规则单一事实源 `rules/quote_rules.json`（版本号 `QT-RULES vX.Y`）。逐条评估规则，命中多条时按严重度取最高并全部留痕；规则的具体设计见 §6.5 |
| 输出 | `RuleResult{clause_id, label_rule, triggered_rules[{rule_id, name, evidence}], surcharge_refs[], missing_fields[], llm_override_allowed:false, llm_may_escalate_only:true, fallback_used, rules_version, audit_id}` |
| 最终标签 | `final = max_severity(label_rule, label_llm)`，严重度：**不满足 > 非标 > 模糊 > 可偏离 > 标配**。LLM 比规则更「宽松」的意见只作为复核线索挂在条目上，不改变标签 |
| 验收 | 1. 规则回归集 ≥ 60 例全部通过；2. 同一输入重复运行 100 次结果完全一致；3. 构造「LLM 判标配、规则判非标」的 10 个用例，最终标签 100% 为非标；4. 引擎抛异常或超时时 100% 输出「模糊 + fallback_used=true」，绝不输出标配；5. 每次输出带 `rules_version` 和 `audit_id` |

### quote-R6 出处与校验

| 项 | 内容 |
|---|---|
| 输入 | 最终判断 |
| 处理 | 组装 `Claim`：`text` = 「第 3.2 条要求面漆 3 遍、总干膜厚 ≥240 μm，超出标配 160 μm，属非标」；`evidence` 至少两类：①协议原文片段（doc、page、字符偏移）；②依据条目（标配库 / 加价标准 / 知识条目）。确定性校验（参考 Loomi `verifyClaimEvidence`）：引用片段规范化后必须在源文本中逐字出现；依据条目必须存在且状态有效；数值必须和片段里的数值一致。校验不过 → 该条改为「模糊 · 依据不足」并提示人工 |
| 输出 | `Claim` + `verified: bool` + `verify_errors[]` |
| 验收 | 出处正确率（引用片段真实存在且支持结论）≥ 95%；人为篡改一个引用片段，校验能 100% 拦下 |

### quote-R7 风险审核（环节 5）

| 项 | 内容 |
|---|---|
| 输入 | 商务类和通用类条款 |
| 处理 | 1. 关键词规则先扫：违约、罚则、罚款、滞纳金、延期、退换货、质保、保修、验收、终验、付款、预付款、尾款、质保金、第三方检验、责任、赔偿、不可抗力、知识产权；2. 参数抽取：罚款比例、罚款上限、质保期、付款节点比例、验收标准、验收地点；3. 阈值规则判风险等级（高 / 中 / 低），阈值见 §6.6（模拟值）；4. LLM 只写「风险说明」和「建议应答」草稿，风险等级由规则定，LLM 只能升不能降；5. 技术条款中「不满足」「可偏离」项自动进入偏离表 |
| 输出 | `RiskItem[]` 和《协议风险提示及技术偏离表（草稿）》（格式见 §8.4） |
| 验收 | 答案集风险条款召回率 ≥ 90%；罚款比例、质保期等数值抽取正确率 ≥ 95%；偏离表可导出 Excel 和 Word |

### quote-R8 人工确认与改判

| 项 | 内容 |
|---|---|
| 输入 | 报价员在界面上对某条判断点「确认」或「改判」 |
| 处理 | 改判必须选新标签 + 填理由（≥10 字）+ 可选「报价思路」；调 `core.review(item)`。**把标签往宽松方向改**（例如非标 → 标配、不满足 → 可偏离）时，标记为「降级改判」，需组长二次确认才计入最终结果（演示时组长和报价员可以是同一人切换角色）；往严格方向改直接生效 |
| 输出 | `ReviewRecord{item_id, from, to, reason, quote_idea, reviewer, time, audit_id}`；触发 R9 |
| 验收 | 每次改判都有审计记录，能回放「规则怎么判、LLM 怎么说、谁改成了什么、理由是什么」 |

### quote-R9 知识沉淀（环节 6）

| 项 | 内容 |
|---|---|
| 输入 | `ReviewRecord`（P0）；口述录音 / 晨会录音（P1） |
| 处理 | 1. LLM 把改判整理成知识条目草稿（格式见 §6.7）：从条款中提炼「条款特征」（去掉客户信息，只留参数模式），写「判断」「判断依据」「报价思路」；2. 自动查重：和已有条目语义相似度 > 0.85 时提示「可能重复 / 冲突」；3. 提交人确认后进入组长审核队列（`core.review`）；4. 组长通过 → 写入 `quote_kb`，立即可检索；退回 → 带意见回到提交人 |
| 输出 | `KnowledgeEntry`（状态：草稿 / 待审 / 已入库 / 已退回 / 已废止） |
| 验收 | 演示中：改判后 ≤ 10 秒出草稿；组长通过后，重新分析另一份含类似条款的协议，该知识条目出现在依据里 |

## 6. Agent / Skill 设计

### 6.1 总体编排

多 Agent，用底座编排器串联（医晓模式）。5 个 LLM Agent + 1 个确定性规则引擎服务 + 1 个确定性出处校验服务。

```text
            ┌──────────────── core.redact（入口）────────────────┐
            ▼                                                     │
   ① ParseAgent ──Clause[]──► ② ClassifyAgent ──Candidate──┐      │
            │                        ▲                      │      │
            │                        │ basis[]              ▼      │
            └──────────────► ③ RetrieveAgent ─────► ④ RuleEngine（代码）
                                                            │ RuleResult（最终标签）
                                                            ▼
                                              ClaimVerifier（代码）
                                                            │
                         ⑤ RiskAgent（规则定级 + LLM 写说明）│
                                                            ▼
                                          报价员确认 / 改判（core.review）
                                                            │ ReviewRecord
                                                            ▼
                                       ⑥ KnowledgeAgent ─► 组长审核 ─► quote_kb
                                                            │
                                         SOP 导出 / QuoteResult ─► C
```

### 6.2 各 Agent 职责与兜底

| Agent / 服务 | 类型 | 职责 | 输入 | 输出 | 兜底 |
|---|---|---|---|---|---|
| ① ParseAgent | LLM + 规则 | 条款切分（规则）、类别与参数抽取（LLM，JSON Schema 约束） | 脱敏文本 | `Clause[]` | 抽取结果必须带原文片段，否则丢弃；Schema 不合法重试 1 次，仍失败该条标「未解析」进人工 |
| ② ClassifyAgent | LLM | 五类候选标签 + 理由 + 升级线索 | `Clause` + `basis[]` | `CandidateJudgement` | 只是候选；失败按「模糊」 |
| ③ RetrieveAgent | 工具调用 | 组织查询、调用 `core.search`、排序依据 | `Clause` | `basis[]` | 查不到依据时 `basis=[]`，规则引擎会因「无标配条目」判模糊 |
| ④ RuleEngine | **确定性代码** | 标配判定、型号一致性、模糊词、加价条目匹配 | `Clause.params` + `basis` + 型号 | `RuleResult` | 异常 / 超时 → 模糊 + `fallback_used`；永不输出标配 |
| ClaimVerifier | **确定性代码** | 出处逐字校验、数值一致性 | `Claim` | `verified` | 校验不过 → 降为「模糊 · 依据不足」（这里的「降」是往严格方向） |
| ⑤ RiskAgent | 规则 + LLM | 风险条款识别（规则）、等级（规则）、说明和建议应答（LLM） | 商务 / 通用条款 | `RiskItem[]`、偏离表 | 等级只能由规则定或 LLM 升级；LLM 失败时说明栏留空，风险项照常列出 |
| ⑥ KnowledgeAgent | LLM | 改判 → 知识条目草稿、查重 | `ReviewRecord` + 条款 | `KnowledgeEntry` 草稿 | 只产草稿，入库必须组长通过 |

### 6.5 规则引擎设计（参考医晓 `rule_engine`）

**照搬医晓的 6 条原则**（来自医晓 `rule_engine/README_规则引擎实现说明.md`，版本 SG-RULES v2.2–v2.5）：

| 医晓原则 | 在本作品中的对应 |
|---|---|
| 规则单一事实源 `rules_definition.json`，前端引擎由脚本生成 | `rules/quote_rules.json` 是唯一来源；界面上的规则说明也从它生成 |
| `llm_override_allowed=false`，LLM「只能补充升级线索并回传引擎复核，不能降低任何分级」 | LLM 只能把标签往严格方向推，或提交「复核线索」；不能把非标改标配、不满足改满足、模糊改标配、风险高改低 |
| 「信息不足禁止判 low」→ `insufficient_info` | **信息不足禁止判标配**：条款涉及某类配套件但关键参数缺失，或出现模糊词，一律判「模糊」 |
| 引擎异常 / 超时走保守回退（一律 high） | 异常 / 超时一律「模糊 + fallback_used」，并进入人工 |
| 冲突时按严重度降序取第一条，全部命中留痕 | 同 |
| 每次输出带 `rules_version`、`audit_id`；回归测试集 | 同；回归集 ≥ 60 例，`python run_tests.py` 一键跑 |
| 否定作用域处理（「否认胸痛」不触发） | 「不要求第三方检验」「无需防爆」不触发对应规则；否定窗口 + 标点截断 |

**标签判定顺序**（每条技术条款）：

1. 能力边界规则命中 → **不满足**（例如工作级别 A8 而标配库只到 A7，跨度超出型号范围且无非标设计说明）
2. 参数超出标配 / 品牌不在标配清单 → **非标**，并挂加价标准条目
3. 关键参数缺失 / 模糊词 / 「或同等」「知名品牌」「按国标」但未写具体标准号 → **模糊**
4. 参数超出标配，但标配库条目标注 `deviation_allowed=true`（例如颜色、资料语种、非关键品牌偏好），且协议没写「不接受偏离」 → **可偏离**
5. 全部参数落在标配范围内，且依据条目存在 → **标配**
6. 以上都不满足（没有对应标配条目）→ **模糊**（不是标配）

**LLM 与规则的关系，用一个例子讲清**：

- 条款：「减速机采用 SEW 或同等品牌」。
- 规则：GBX-01 命中「SEW」→ 非标；GBX-03 命中「同等」→ 模糊。按严重度取非标，两条都留痕。
- LLM 候选：「可偏离，可用蒲瑞替代」。
- 最终：**非标**。LLM 的意见挂成复核线索：「LLM 认为可按『同等品牌』申报蒲瑞，需要报价员判断客户是否接受」。报价员如果确认改为可偏离，这是降级改判，需要组长二次确认，并自动生成知识条目。

## 10. 验收标准与评测

### 10.1 指标

| 指标 | 定义 | 目标（P0） |
|---|---|---|
| 非标点召回率（关键） | 答案集中「非标 + 不满足」被系统标出（标签一致或更严格）的比例 | ≥ 90% |
| 五类召回率（全部） | 答案集中非标 / 模糊 / 不满足 / 可偏离各类被正确标出的比例，分类别报告 | 非标、不满足 ≥ 90%；模糊、可偏离 ≥ 75% |
| 准确率 | 系统标为非标 / 模糊 / 不满足 / 可偏离的条目中，与答案集一致的比例（标配干扰项被误标计入错误） | ≥ 80% |
| 漏报危险率 | 答案集为非标 / 不满足，系统最终标为「标配」的数量 | **0**（硬指标） |
| 出处正确率 | 判断的引用片段真实存在于原文、依据条目正确、数值一致的比例（人工抽查 + 自动校验） | ≥ 95% |
| 依据命中率 | 期望依据条目出现在 top-3 的比例 | ≥ 90% |
| 风险条款召回率 | 答案集风险条款被标出的比例 | ≥ 90% |
| 风险数值正确率 | 罚款比例、上限、质保期、付款比例等抽取正确的比例 | ≥ 95% |
| 规则确定性 | 规则回归集通过率；同输入重复运行一致率 | 100% / 100% |
| LLM 越权率 | 最终标签比规则标签宽松且未经人工确认的条目数 | **0**（硬指标） |
| 脱敏覆盖率 | 埋入的客户名、人名、电话、金额被替换比例 | 100% |
| 节省时间 | 见 10.2 | 目标：单份协议从人工 X 分钟降到 ≤ X/3（实测） |
| 处理耗时 | 20 页协议从上传到出全部结果 | 云端 ≤ 3 分钟；本地模式 ≤ 8 分钟（待本地模型实测） |

### 10.2 节省时间怎么测

- **对照组**：请 1–2 名（理想是报价部的）同事，或开发者本人，拿 T1 纸质 / PDF 协议人工逐条阅读，填同样格式的非标清单和风险表，计时，同时记录漏掉的点。
- **实验组**：同一人用系统处理 T2（避免记忆效应，T1 / T2 交叉），计时包含逐条确认和改判。
- 报告：人工用时、系统 + 复核用时、各自召回率。**不预设人工用时**，以实测为准；如果拿不到报价部同事，在答辩材料里注明「对照组为开发者本人」。

### 10.3 测试样例

| 样例 | 用途 |
|---|---|
| 3 份模拟协议 + 答案集 | 主评测 |
| 规则回归集 ≥ 60 例 | 每条规则正例、反例、否定、模糊词、缺参、冲突、异常回退 |
| 越权测试 10 例 | 构造 LLM 宽松、规则严格的用例，验证最终标签不被放宽 |

| 版本测试 5 例 | 加价标准 v1 / v2，验证只引用最新生效版本 |
| 脱敏测试 | 每份协议埋 ≥ 5 个敏感字段 |
| 断网测试 | 本地模式全流程 |

| 模拟标配值和卫华真实标准差距大，评委（报价部）一眼看出 | 可信度下降 | 所有模拟值打「模拟」水印；答辩时强调「标准值是数据，机制是重点，拿到真实标配库替换 JSON 即可」；争取赛前拿到脱敏样例 |
| 模拟协议写得太规整，召回率虚高 | 评测不可信 | 协议措辞多样化、埋隐蔽点；如有可能用 1 份真实脱敏协议做盲测 |
| 本地模型抽取质量不够 | 本地模式下召回率下降 | 规则引擎和关键词扫描不依赖模型；本地模式单独报告指标；演示时本地模式只跑短协议 |
| PDF 版式复杂（表格、跨页） | 条款切分错误、高亮位置错位 | P0 只承诺带文字层的 PDF / Word；表格按行切；答案集里标注「隐蔽」难度单独统计 |
| 「可偏离」判断高度依赖商务经验 | 准确率低 | 规则只在标配库标注 `deviation_allowed` 时判可偏离；其他交给人工，这本身就是知识沉淀的来源 |
| 和售前软件被认为重复 | 答辩扣分 | 「差异化」一节；演示开头就讲 |
| 和上届一等奖「让工程经验成为 AI 的可用资源」被认为相似 | 新意不足 | 强调经验来自日常改判（零额外工作量）、有审核和规则化通道、和非标识别闭环 |
